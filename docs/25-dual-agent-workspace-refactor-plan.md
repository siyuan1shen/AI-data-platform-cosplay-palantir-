# 25 双 Agent、双工作台重构计划

> 更新说明：平台边界、项目归属、Agent 入口和交接方式以 [26 开发者平台与高管使用者平台拆分计划](26-developer-executive-platform-split-plan.md) 为准。本文件继续约束两个 Agent 的职责、工具化能力和上下文原则。

## 1. 重构结论

本次重构不再把每项能力都设计成一个 Agent。产品只保留两个用户可见的主 Agent：

1. **企业投影 Agent**：由顾问、项目负责人或实施人员使用，负责把问卷、报告、现场材料和系统数据建设成企业数字投影。
2. **管理决策 Agent**：由企业核心管理层使用，负责在已发布的数字投影上理解企业、分析问题、比较方案、形成决策并跟踪行动。

本体、数据映射、因果、报告、学习和证据检查都属于工具或后台服务，不再增加用户需要选择的 Agent 数量。

核心原则：

> Agent 是面向不同使用者和上下文的推理入口；工具才是具体能力。避免上下文污染，应通过工作台边界、发布版本和上下文快照实现，而不是继续拆分 Agent。

## 2. 产品角色重新定义

### 2.1 企业投影 Agent

服务对象是负责企业调研、建模和系统接入的人员。

主要任务：

- 读取外部问卷系统导出的问卷和报告；
- 提取事实、观点、证据、冲突和缺口；
- 识别企业对象、对象类型、属性和关系；
- 统一不同系统中的名称、编号和身份；
- 建议字段映射、转换规则和数据质量处理；
- 通过变更集创建或修改投影中的对象、关系、事件和指标；
- 检查投影完整性；
- 生成待确认的投影版本；
- 在人工确认后发布投影版本。

它回答的是：

> 这家公司在数字世界中由什么构成，数据如何证明这些对象和关系？

它不负责：

- 设计外部问卷；
- 代替外部问卷系统发起追问；
- 直接替管理层作决策；
- 把未经确认的推断写成正式企业事实；
- 修改已经发布的投影版本。

### 2.2 管理决策 Agent

服务对象是企业董事长、总经理、核心管理层和经授权的决策参与者。

主要任务：

- 用自然语言查询企业当前状态；
- 从对象关系、事件、指标和证据中解释问题；
- 识别和排序管理问题；
- 提出可证伪的因果假设；
- 比较管理方案、成本、风险、影响和停止条件；
- 形成决策草案和行动计划；
- 跟踪行动执行结果；
- 生成管理层报告；
- 发现数字投影缺口并发起“投影补充请求”。

它回答的是：

> 企业现在发生了什么，为什么发生，管理层可以采取什么行动，行动结果如何？

它不负责：

- 直接修改原始问卷、报告或系统数据；
- 直接修改本体和跨系统映射；
- 把草稿投影当成正式事实；
- 绕过投影发布版本读取未确认内容；
- 用没有证据的语言替管理层下结论。

## 3. 两个工作台，而不是一个 Agent 下拉列表

### 3.1 投影工作台

面向企业投影建设人员，页面顺序为：

1. 项目范围和初始关切；
2. 问卷答案、调研报告和现场材料导入；
3. 材料解析与事实确认；
4. 对象、类型和关系建模；
5. 系统数据导入与字段映射；
6. 数据质量和身份冲突处理；
7. 投影完整性检查；
8. 创建投影版本；
9. 人工确认并发布。

工作台中只有一个对话入口：企业投影 Agent。页面上的本体、数据接入和校验是它可以调用的工具，不是新的 Agent。

### 3.2 管理驾驶舱

面向企业高管，页面顺序为：

1. 企业概览；
2. 关键经营指标和变化；
3. 关键管理问题；
4. 管理决策 Agent 对话；
5. 证据和数据路径；
6. 情景与方案比较；
7. 决策记录；
8. 行动计划与执行状态；
9. 结果复盘与报告。

高管不需要看到导入批次、字段映射、本体草稿、技术变更集和内部 Agent 运行日志。必要时，管理决策 Agent 可以用证据链接解释结论，但不把实施细节强行放进主界面。

## 4. 两个工作台之间唯一正式交界面

使用“已发布企业投影版本”作为边界：

```text
投影工作台：草稿数据、候选模型、变更集
                  ↓ 人工确认并发布
已发布企业投影版本
                  ↓ 只读消费
管理驾驶舱：诊断、因果、决策、行动和报告
```

管理决策 Agent 默认只读取最新的已发布版本。投影工作台可以继续建立下一版草稿，但不会影响管理层当前看到的版本。

当管理决策 Agent 发现缺口时，只生成投影补充请求，例如：

> 请补充客户流失与售后响应时间之间的对象关系，并接入近 12 个月数据。

请求回到投影工作台处理，完成后生成新版本再发布。管理层现有的决策和报告仍然绑定原来的投影版本。

当前代码已有 `projection_versions` 和 `ontology_releases`。重构时不重复建设第三套版本系统：

- `projection_versions` 继续记录技术变更提交序列；
- `ontology_releases` 继续记录本体发布包；
- 新增轻量的 `projection_publications`，绑定一个可供管理层消费的投影序列、本体发布包、数据快照和校验结果。

## 5. 上下文契约

### 5.1 投影 Agent 上下文

允许读取：

- 当前项目简报；
- 问卷和报告；
- 现场材料及附件；
- 调研答案、发现和证据；
- 当前本体草稿和历史发布版本；
- 对象、关系、事件和指标；
- 系统导入样本、字段映射和数据质量结果。

允许提出：

- 事实候选；
- 对象和关系候选；
- 类型和别名候选；
- 字段映射和转换规则；
- 数据质量问题；
- 投影变更集；
- 投影发布建议。

禁止：

- 直接创建正式管理决策；
- 直接执行管理行动；
- 将管理层的未确认意见写成企业事实；
- 读取其他公司的项目数据。

### 5.2 管理决策 Agent 上下文

允许读取：

- 当前已发布投影版本；
- 已确认对象和关系；
- 已确认事件、指标和数据观察；
- 有来源的发现和正式管理问题；
- 因果假设、历史决策、行动和结果；
- 投影发布时的校验摘要。

允许提出：

- 管理问题候选；
- 因果假设；
- 方案和情景；
- 决策草案；
- 行动计划；
- 投影补充请求；
- 管理报告草稿。

禁止：

- 读取投影草稿并把它当作已确认事实；
- 直接覆盖本体、对象、关系或原始数据；
- 直接把自然语言回答写成正式决策；
- 在没有依据时声称因果关系已经成立。

## 6. 现有 Agent 的处理结果

| 旧 Agent | 重构后的归属 | 处理方式 |
|---|---|---|
| 项目总控 | 系统流程控制器 | 不再作为用户 Agent |
| 调研 | 企业投影 Agent | 改名为材料理解能力 |
| 追问 | 无 | 删除，不重复外部问卷系统 |
| 本体 | 企业投影 Agent 工具 | 保留能力，不保留入口 |
| 数据接入 | 企业投影 Agent 工具 | 保留能力，不保留入口 |
| 诊断 | 管理决策 Agent 工具 | 由管理 Agent 调用 |
| 因果 | 管理决策 Agent 工具 | 由管理 Agent 调用 |
| 决策 | 管理决策 Agent 工具 | 与行动能力合并 |
| 行动 | 管理决策 Agent 工具 | 与决策能力合并 |
| 学习 | 后台飞轮服务 | 行动有结果后自动触发 |
| 报告 | 报告生成服务 | 由管理 Agent 调用 |
| 批评 | 系统校验层 | 自动检查，不单独聊天 |

## 7. 数据和 API 重构方案

### 7.1 Agent 对话

新增两个正式概念：

- `projection`：企业投影工作台对话；
- `management`：管理驾驶舱对话。

现有 `agent_threads.agent_kind` 不立即删除，迁移期间保留旧值用于历史记录。新增 `workspace_kind` 作为正式字段，并建立映射：

```text
project / research / followup / ontology / integration → projection
diagnosis / causal / decision / action / learning / report / critic → management
```

新前端只创建 `projection` 或 `management`。旧 API 继续接收旧值并自动映射，避免历史数据和测试失效。

### 7.2 Agent 运行

现有 `AgentService` 的四个旧底层角色不能继续作为用户理解的 Agent 类型。重构后：

- Agent 运行记录增加 `workspace_kind`；
- 每次运行记录使用的投影版本或发布版本；
- 工具调用记录真实的输入、输出和状态；
- 运行结果仍然只能生成提案或变更集，不能绕过人工确认；
- 离线模式继续可用，但明确标记为本地规则响应，不冒充模型推理。

### 7.3 投影发布

新增 `projection_publications`，至少包含：

- 项目 ID；
- 发布编号；
- 对应投影序列；
- 对应本体发布 ID；
- 数据导入检查点；
- 投影校验结果；
- 发布说明；
- 状态；
- 创建和发布时间。

正式管理问题、因果假设、决策和报告新增可追溯的发布版本引用。历史数据没有引用时保留为空，并按旧数据兼容规则展示。

## 8. 前端重构顺序

### 第一步：减少 Agent 选择

删除 12 个 Agent 按钮，改成两个工作台入口和两个对话列表。旧对话按映射结果归档到对应工作台，不删除历史。

### 第二步：重命名用户语言

- “Agent 工作台”改为“投影工作台”或“管理驾驶舱”；
- “工作结果”改为“投影变更建议”或“决策建议”；
- “交接给下一位 Agent”改为“提交到另一工作台”或直接取消；
- 删除“追问 Agent”和“批评 Agent”相关文案。

### 第三步：加入发布边界

投影工作台显示：

- 当前草稿版本；
- 最新已发布版本；
- 草稿与已发布版本差异；
- 投影校验状态；
- 发布按钮。

管理驾驶舱显示：

- 当前消费的投影版本；
- 版本时间和范围；
- “发现数据缺口”按钮；
- 创建投影补充请求的入口。

### 第四步：隐藏工程细节

本体发布、导入批次、变更集和 Agent 运行日志仍然保留给投影建设人员，但不出现在高管默认页面。高管页面只出现管理问题、证据、指标、方案、行动和结果。

## 9. 分阶段编码计划

### R0：冻结基线

- 保存当前数据库备份；
- 固定问卷答案导入、麦数科技真实项目和现有报告测试；
- 记录当前 Agent 对话和历史数据数量；
- 不删除旧表、不覆盖历史记录。

出口：现有全量测试通过，重构前后可以比较数据数量和报告结果。

### R1：后端概念和迁移

- 新增 `AgentWorkspaceKind`；
- 新增 `workspace_kind` 字段和兼容映射；
- 新增投影发布模型和迁移；
- 为管理对象增加发布版本引用；
- 增加正式的投影上下文和管理上下文构建器。

出口：两个工作台可以分别读取正确范围的上下文，旧 API 仍然可用。

### R2：企业投影 Agent

- 合并材料理解、本体、数据接入工具；
- 保留变更集和人工确认机制；
- 问卷答案导入成为主要材料入口；
- 去除自动追问相关产出；
- 增加投影差异和发布前检查。

出口：使用问卷和报告可以从材料导入走到投影发布。

### R3：管理决策 Agent

- 只绑定已发布投影；
- 合并诊断、因果、决策、行动和报告工具；
- 允许创建问题、假设、方案和行动草案；
- 增加证据路径和版本引用；
- 支持投影补充请求。

出口：高管只通过一个 Agent 完成“提问—解释—决策—行动—复盘”。

### R4：前端双工作台

- 用两个明显入口替换多 Agent 列表；
- 分离投影建设页面和管理驾驶舱页面；
- 按使用者隐藏不必要的工程细节；
- 保留对话创建、删除、恢复和附件功能；
- 让所有提交动作在页面上显示其影响范围和目标版本。

出口：新用户无需理解 Agent 专业名称即可完成完整流程。

### R5：内部校验和后台学习

- 将批评能力改为提案自动校验；
- 校验失败时给出具体证据缺口，而非泛化批评；
- 行动结果触发学习资产候选；
- 学习资产回流投影 Agent 的可复用知识库；
- 不增加新的用户 Agent 入口。

出口：每个关键提案都有来源、版本和校验状态，行动结果能够形成下一轮改进材料。

### R6：迁移清理

- 新前端不再创建旧 Agent 类型；
- 旧类型仅保留兼容读取和迁移脚本；
- 更新使用手册、流程文档和演示数据；
- 删除追问入口和批评入口；
- 在连续一个版本周期无旧调用后，再评估删除旧字段和旧 API。

出口：产品、代码、文档和测试都只把两个主 Agent 作为正式产品概念。

## 10. 必须通过的真实验收场景

### 场景 A：投影建设人员

1. 新建麦数科技项目；
2. 导入问卷答案 CSV；
3. 上传初次、第二次、第三次调研报告；
4. 让企业投影 Agent 提取事实、对象和关系候选；
5. 人工确认对象、关系和数据映射；
6. 运行投影校验；
7. 发布投影版本；
8. 查看版本差异和来源。

### 场景 B：企业高管

1. 进入管理驾驶舱；
2. 询问“公司当前最值得关注的问题是什么”；
3. 管理决策 Agent 只引用已发布投影；
4. 点击查看证据、对象路径和指标；
5. 形成问题候选、因果假设和决策方案；
6. 确认行动计划；
7. 记录执行结果；
8. 生成管理报告。

### 场景 C：投影版本变化

1. 高管发现“客户流失缺少售后数据”；
2. 管理决策 Agent 创建投影补充请求；
3. 投影建设人员修改草稿投影；
4. 发布新版本；
5. 新版本可以被新的管理分析使用；
6. 旧报告仍然引用旧版本，内容不被悄悄改写。

### 场景 D：上下文隔离

1. 投影 Agent 不能看到其他项目；
2. 管理 Agent 不能把投影草稿当作正式版本；
3. 删除对话不删除已确认投影和决策；
4. Agent 不能绕过变更集、发布和人工确认；
5. 两个 Agent 的运行日志能说明使用了哪个版本和哪些工具。

## 11. 明确不做的事情

- 不再增加追问 Agent；
- 不再增加批评 Agent 用户入口；
- 不为本体、因果、报告等每项能力各建一个 Agent；
- 不让高管直接操作字段映射和本体草稿；
- 不让管理 Agent 直接改写企业投影；
- 不为了“看起来多 Agent”而保留重复的角色名称；
- 不删除历史对话和旧数据来换取表面上的结构整洁。

## 12. 完成定义

重构完成必须同时满足：

- 前端只展示企业投影 Agent 和管理决策 Agent 两个主入口；
- 问卷和报告可以直接进入企业投影建设流程；
- 投影草稿和已发布投影严格区分；
- 管理决策 Agent 只能基于已发布投影工作；
- 管理层可以完成提问、解释、决策、行动和复盘；
- 投影人员可以完成导入、建模、映射、校验和发布；
- 批评能力已经成为自动校验，不再是额外对话步骤；
- 追问能力已经从 Palantir 产品流程中移除；
- 旧数据、旧报告和旧 API 仍然可以读取；
- 通过多公司、多项目、多版本和多角色的端到端测试。
