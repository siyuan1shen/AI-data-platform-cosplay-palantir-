# 企业管理决策投影平台：最终开发规格

版本：1.2；日期：2026-09-12；状态：总体分阶段实施中；实模/虚模及岗位专项新增契约待实施。

本文是下一轮重构的唯一总规格，整合三库、四个 Agent、任务路由、Action、人工留痕及真实系统验收。与早期规划冲突时，以本文为准。本文的“实现”“必须”均指交付要求，不代表现有程序已具备该能力；运行状态与验收证据另行记录。

1.1 引入岗位专项；1.2 将其调整为与原企业实模关联、独立版本的虚模，修改第 23 章并增加第 24 章路由与风险契约。FDE 先实地提效，子 Agent 再整理细节；不自动分解、下达管理目标或调整员工职责。以第 24 章为最新约束，替代旧有“岗位细节确认后整体进入正式库/默认查询”的设计。第 2 章保留 1.0 编制时的代码核对快照，不代表之后的实时实现状态。

## 1. 产品目标与范围

所有企业先通过问卷、访谈、制度和现场材料建立企业投影；有信息系统的企业再接入运行数据。管理者通过统一入口了解企业、查询数据、探索隐藏问题、比较方案和推进行动。

必须达成四条业务链：

1. 材料 → 有来源的模型草稿 → 人工修订 → 发布 → 可查询的企业图。
2. 日常信息 → 观察 → 跨库调查 → 人工确认潜在认识 → 持续验证和纠错。
3. ERPNext → 原始快照 → 映射与身份对齐 → 校验 → 统一查询、计算和导出。
4. 明确任务 → 程序路由 → 注册动作 → 执行回查 → 管理实施反馈 → 复盘。

产品提供开发端和管理端，切换时保持公司及项目上下文。公司和项目创建、建模、接入、映射、发布及扩展安装归开发端；管理者查询、提供信息、确认认识和推进行动归管理端。

本轮不建设行业专业调度/排程算法、通用微服务平台、集中云端行业飞轮、复杂安全治理产品、任意代码执行器或自动模型训练。历史相似企业可由用户明确选择后作为参考，不能自动并入本企业事实。

## 4. 存储、所有权与版本

### 4.1 公司与项目的作用

公司是企业对象身份及业务数据的边界；项目是某次建模、调查或改进工作的范围，不能让同一公司每新建一个项目就生成独立的客户、岗位和员工身份。

每个项目指定一个已发布企业模型版本；草稿分支只在开发预览中可见。管理对话读取项目当前选用的发布版本，业务数据则使用任务声明的观察时间和同步批次。发布版本变化时提示并记录切换，进行中的任务不静默改变基线。

跨项目共享公司主数据，通过明确对象引用实现；跨公司参考必须由人指定参考企业/案例。借鉴的结构成为本公司待验证草稿，不复制真实对象标识和来源认可状态。

### 4.2 正式企业库 formal.db

| 资源组 | 关键资源 | 约束 |
|---|---|---|
| 身份与建设 | Company、Project、Entity、IdentityAlias、ModelBranch、Publication | 公司内稳定标识；项目引用模型版本 |
| 本体与设计 | ObjectType、RelationType、PropertyDefinition、ModelRevision、EntityRevision、RelationRevision | 类型、端点、基数、有效时间、版本、来源 |
| 系统与对齐 | SourceSystem、SourceAsset、SourceIdentity、MappingVersion、RelationMapping、SyncRun | 源身份为 source+doctype+name，不以显示名唯一 |
| 正式运行数据 | CanonicalRecord、BusinessEvent、MetricDefinition、MetricResult、Dataset | 业务口径、来源记录、转换版本、批次、数据时间 |
| 管理落实 | Decision、ManagementAction、ActionDependency、OutcomeObservation | 决策、行动、报告完成及效果证据分别记录 |

隔离导入区存放 RawBatch、RawRecord、ValidationResult 和 SourceConflict，使用单独的仓储接口，普通正式查询不能访问它。源文件和原始 API 响应以不可变文件保存，数据库只持有摘要和定位。校验通过的记录进入正式查询视图；不确定部分保持隔离，不伪装成成功批次。

正式库区分设计状态和实际记录。制度授权人与系统操作人不同可能是不同语义；应保留两种关系并生成比较结果。人工发布表示组织认可模型，不证明该模型必然等同现实。

### 4.3 管理观察库 observations.db

资源：ObservationSource、SourceFragment、Observation、ObservationRevision、ObjectMention、ObservationLink、DuplicateCluster、Contradiction、IngestionRun。

Observation.kind 至少区分 EVENT、STATEMENT、OPINION、REQUEST、HEARSAY、INFERENCE。原文是输入记录，提取文本是机器解释，两者不可互相替代。

字段包括 occurred_at/时间范围、recorded_at、speaker（可未知）、submitted_by、来源片段、关联对象、提取模型与运行、对象匹配状态及修订状态。不能由提交者自动推导发言者，不能把录入时间填成事件时间。

“管理者确认录入正确”只确认陈述被准确记录，不等于确认陈述中的所有事实。

### 4.4 企业潜在库 potential.db

资源：PotentialRecord、PotentialRevision、EvidenceLink、CounterEvidenceLink、ValidationPlan、ReviewEvent、OutcomeLink。

类型：潜在关系、问题假设、设计权衡、因果假设、管理经验。每条必须包含明确表述、适用对象和时间、来源任务、支持证据、已知反例、未知项及后续验证方式（可标尚未定义）。

状态分离：

- 人工：ACCEPTED、REJECTED、WITHDRAWN。待确认候选保存在控制库，不属于已认可潜在知识。
- 证据：UNTESTED、SUPPORTED、CONTESTED、REFUTED、STALE。
- 任意记录可标记 NEEDS_REVIEW，不自动由 SUPPORTED 降成 REFUTED。

默认检索纳入 ACCEPTED 且未撤回的记录，并显著保留证据状态。REFUTED/WITHDRAWN 只作历史、反例或防止重复提出的材料，不算当前正向依据。

潜在库的默认参考地位高于未经整理的观察，低于相关领域的正式依据；这不是逐条自动的概率排序。正式记录本身被质疑时可调查，但只能通过独立更正流程修正。

### 4.5 控制库 control.db

资源：Actor、Conversation、MessageRevision、Task、TaskSpec、TaskRoute、QueryManifest、EvidenceRead、ClaimLedger、ToolCall、ActionDefinition、ActionInvocation、Approval、PotentialCandidate、OperationReceipt、Job、EventInbox、AuditIndex。

Company 标识注册以正式库为主，控制库只引用；对话不是另一份正式企业知识。

所有库使用 UTC 记录时间，界面按公司时区显示；业务区间采用显式起止。金额用 Decimal，币种与换算依据明确；不得用二进制浮点代替金额口径。缺失、未知、未发生和零分别处理。

## 5. 跨库一致性、备份与恢复

不假设四个数据库能完成一个全局事务。每次操作生成 operation_id：

1. 控制库存储人类提交/Agent 提议及状态 RECEIVED；失败则不开始有副作用步骤。
2. 目标库事务同时提交业务变更、完整的本地审计事件和已处理 operation_id。
3. Worker 按至少一次投递把事件复制到控制库审计索引；event_id 唯一去重。
4. 控制库记录目标库提交证据后回报成功；未确认时显示处理中/待核对，允许安全重试状态查询。

目标库宕机可重试相同 operation_id；已提交但回执丢失时必须读取目标库回执，不能重复创建。多库流程记录每步状态；已经发生的外部效果不因本地回滚而被宣称消失。

源库审计事件为本地权威记录，控制库为可重建聚合索引。传输标记可更新，审计正文不可改写。定期一致性检查报告孤立引用、未同步事件和未终结操作。

备份时进入短暂写入栅栏，等待在途本地写入结束，用 SQLite backup 接口保存四库及文件清单，记录共同 checkpoint 和未完成动作。不能直接复制正在写入的 SQLite 主文件。恢复先校验版本/摘要，在新目录验证，再切换；外部动作按回查结果恢复状态，不能恢复后自动重放。

## 6. 企业建模与图交互

核心对象覆盖公司、部门、岗位、角色、人员（有需要时）、流程、流程步骤、职责、权限、战略目标、能力、知识、系统、指标及外部对象。

关系覆盖隶属、汇报、承担、授权、审批、执行、输入输出、交接、支持战略、接受考核及明确的资金/信息/物流/指令流。岗位职责、设计理由、工作价值、可量化范围、难量化部分和结构性权衡有独立字段或可查询关系，不能只放一段不可关联的大文本。

流程：材料 → 引用片段 → 建模草稿 → 类型/关系校验 → 差异预览 → 人工编辑或自然语言修订 → 发布。

图支持按组织/流程/权限/战略考核/系统关联切换视图，节点展开、搜索、图例、边方向、来源与时间。大图分页加载邻域，布局坐标单独存储。节点和关系可增删改查；删除为退役，保留被历史引用的版本。潜在联系作为可切换的虚线叠层，不能显示得像正式关系。

建模不要求先接 ERP。对未充分覆盖的材料标注范围，不允许通过通用模板捏造具体公司事实。模板和相似公司只产生可确认草稿。

## 7. 四个 Agent 与工具边界

| 角色/代码标识 | 读能力 | 写能力 | 不允许 |
|---|---|---|---|
| 建模 PROJECTION | 原始调研、正式草稿/发布、与变更相关的观察和潜在认识 | 生成、修订、校验模型变更；提交发布请求 | 把潜在记录自动转正式关系；擅自改系统业务记录 |
| 本体 SYSTEM_ONTOLOGY | 源结构与样本、正式本体、映射、身份、数据冲突及相关语义说明 | 建议/配置映射、受控同步、物化、身份绑定、统一查询 | 猜测主键或单位；用相似名称自动合并不确定对象 |
| 输入 MANAGEMENT_INPUT | 提交材料、相关对象/时间、重复与冲突候选 | 观察录入、修订、撤回、链接和冲突建议 | 写正式设计；自己确认潜在知识 |
| 输出 MANAGEMENT | 三库相关信息、发布模型、行动和选定案例 | 任务、分析、候选、管理行动、注册外部动作；提出正式变更请求 | 直接改可信模型；伪造确认；执行未安装动作 |

共用 QueryGateway 提供按需读取，不以初始对话上下文限制信息范围。各 Agent 的模型可配置，MOCK 仅用于机械流程与测试；未启用真实模型时不得宣称具备自由探索能力。

跨角色交接传递结构化任务、对象、来源和版本，不转述一段无依据的摘要。输出端创建正式变更请求后，回报等待开发端处理，不能把交接完成写成模型已更新。

岗位实际工作专项作为 PROJECTION 下的 WORK_PRACTICE 子 Agent 配置，使用独立任务上下文和受限工具集，复用结构校验/审计组件，但写入目标固定为观察库中的虚模资源。它不新增企业身份注册表或物理数据库，不能继承实模写入权限。详细契约见第 23–24 章。

## 8. 管理输入链

1. 保存用户提交的原文/文件及哈希，提交即留痕。
2. 解析材料并提取片段；不支持格式返回明确结果。
3. Agent 区分事件、陈述、评价、诉求、转述和推测。
4. 程序校验片段存在、公司边界、时间格式和对象标识。
5. 重复来源合并为关联，不覆盖不同人的原始陈述；冲突保留。
6. 保存观察及提取修订；返回保存数量、关联对象及待确认项。

首轮支持沿用已验证的 CSV/JSON/TXT/DOCX 与文本型 PDF 解析；以能力清单逐项验收。扫描 PDF/OCR、音视频只有对应解析器实际启用才显示支持。表格需保存列映射与源行定位。

在管理输出对话中主动补充的新信息自动进入同一录入流程，并提示已作为观察保存。分析答案不会被当成人类原话再次录入。输入失败保留原提交和失败记录，不能显示已吸收。

## 9. 任务路由与程序判定

TaskSpec 字段：goal、company_id、project_id、model_release_id、intent、targets、time_range、metric_ids、requested_effects、candidate_tools、ambiguities、explicit_exploration。

模型解析自然语言；后端核验标识、动作模板、口径、来源、时效、冲突及执行条件，并输出：SIMPLE、COMPLEX 或 NEEDS_INPUT。WAITING_DATA 为执行等待原因，不算第三种分析模式。

### 9.1 简单任务准入

- 查询/计算仅依赖已发布模型和校验通过的正式数据。
- 存在注册查询或动作模板，参数明确。
- 所需对象唯一，公式、单位、时间和聚合路径明确。
- 缺失数据或相关冲突不会被忽略。
- 不需要解释隐含原因、组织重设计或管理权衡。

用户明确保存一条观察、确认候选或创建行动也可作为简单指令执行；这表示操作明确，不表示写入的内容被验证为事实。

程序保证模板执行一致，不能保证模型第一次语义解析永远正确。对金额、时间、目标对象及外部动作展示可读的结构化参数，保留纠正入口；歧义时请求补充。

成功显示“简单任务”与答案/结果，无需默认展开依据。后台保留完整取数和执行依据。任何失败、未知或不足必须直接显示。

### 9.2 复杂任务

显式探索，或需要潜在联系、原因解释、非结构化证据和方案权衡时进入 COMPLEX。可以按任务需要读取全部三类库的相关数据。缺失确定性数据不能自动变成 AI 自由推断。

任务可混合：程序统计 → 跨库解释 → 人选方案 → 注册动作执行。任务类型与动作确认策略独立；读复杂分析不增加无意义确认，简单外部写入也必须满足其动作条件。

路由原因保存为规则命中和缺项列表，不能只保存模型输出的“我认为简单”。

## 10. 复杂调查与潜在问题识别

调查由以下三个视角组成，但不再新增三个常驻 Agent：

- 设计侧：战略、职责、授权、流程、考核、可量化/难量化工作及必要权衡。
- 结果侧：业务记录、会议、绩效、现实反馈和时间变化。
- 综合探索：第一性原理、替代组织方案、非正式影响、知识依赖、激励与风险耦合。

工具可以帮助读取和核对，不能把探索限制为固定五个配方。管理探索模块提供可版本化的提示、分析视角和输出结构，后续可以添加新的管理理论和检查方式。确定性规则的告警与模型产生的假设明确分开。

设计与结果相互支持时显示“线索相互印证”；只有设计侧时为结构预警；只有结果侧时为待解释异常；存在反例时显著展示。此分类用于调查优先级，不自动证明因果或管理最优方案。

### 10.1 检索与覆盖

先提供企业概况和任务对象，再分页搜索、读取原文、扩展图邻域、查看相关时间和反例。QueryManifest 记录每个库的版本/水位、对象/时间/来源覆盖、截断、失败和缺口。

首轮本地索引采用可增量更新的全文检索与对象/时间过滤。中文必须进行可测试的分词或字符 n-gram 预处理，不能默认英文分词器能完成中文检索。语义向量检索为可插拔增强，未配置时明确能力；不能让向量相似度代替身份确认或证据。

多轮扩展停止条件是相关覆盖满足、没有新证据或达到可配置预算。达到预算时回报部分完成及未覆盖范围，支持续查。源记录撤回后同步失效索引与缓存，审计副本不进入普通检索。

### 10.2 可核验结论

每项重要结论生成 ClaimLedger：表述、事实/假设类别、支持引用、反例、适用范围和未知项。程序验证引用存在、版本及边界、计算结果与工具输出一致；语义是否足以支持因果仍由分析与人判断，不能宣称程序已证明。

复杂回复顺序固定：执行说明 → 数据与依据 → 结论和替代解释 → 建议/已执行动作 → 潜在候选确认。执行说明由真实工具轨迹和覆盖记录组成；不展示模型隐私推理链，也不以其替代证据。

## 11. 潜在库确认协议

Candidate 包括 candidate_id、revision、payload_hash、公司、对象、具体内容、支持/反例和适用时间。用户确认请求携带该版本及哈希；服务从实际用户会话确定 confirmed_by，不接受 Agent 自报确认人。

人工可逐条接受、修改后接受、合并、拒绝、暂缓。编辑形成新 revision，旧确认失效。确认合并展示被合并内容的差异，不能覆盖另一条已认可的意见。

管理者明确说“将以下内容加入潜在库”即是这次授权；系统生成可读保存回执。内容边界模糊时先澄清。Agent 自发提出的候选必须等待人确认，超时和离开页面不算同意。

证据晋升必须依赖新来源或实际验证结果；反复运行 Agent 和重复引用不得累积虚假支持。出现反证或基线变动时标 NEEDS_REVIEW；保留原结论和谁修改了它。

晋升正式信息是独立操作：创建正式变更请求、领域校验、差异预览、相应人员确认。保留潜在记录作为形成过程，不做移动后删除。

## 12. Action 规格与工作流

### 12.1 两种不同对象

- ActionInvocation：一次程序操作，例如导出、写记录、调用接口。
- ManagementAction：现实管理行动，例如在两周内调整审批流程，由负责人推进，可包含多个程序操作和人工步骤。

调用创建整改任务成功，只能证明任务已创建。人工报告实施完成标记 REPORTED_DONE；检查交付证据后为 VERIFIED_DONE；效果继续用 OutcomeObservation 追踪。

### 12.2 ActionDefinition 必填契约

key/version、input_schema/output_schema、allowed_agents、effect_kind、target_type、scope、preconditions、required_evidence、confirmation_policy、prepare、execute、verify、idempotency_strategy、timeout、retry_policy、compensate（可不支持）、audit_fields、contract_tests。

参数、范围、定义版本及预演结果组成 plan_hash，确认绑定该哈希和有关版本。输入或关键数据变化必须重新校验，不能复用过期批准。

读取类不必假装进行写入预演；外部接口不能预演时给出操作计划及“未运行服务端预演”，禁止用真实写入冒充 dry-run。

### 12.4 状态与恢复

Invocation：PROPOSED → VALIDATING → READY 或 WAITING_INPUT/WAITING_APPROVAL → RUNNING → VERIFYING → SUCCEEDED。

分支状态：FAILED、CANCELLED、OUTCOME_UNKNOWN、PARTIAL、COMPENSATION_PENDING、COMPENSATED。确认后再次校验版本。失败保留失败阶段；不能把执行返回 HTTP 200 直接当业务成功。

外部写入持久化 invocation_id 和关联标识后执行。响应丢失进入 OUTCOME_UNKNOWN，先回查；无法确认时等待人工核对，不盲目 POST 重试。外部系统不提供幂等能力时不得声称 exactly-once。

人工步骤可等待、提醒（需启用相应能力）和记录反馈。长期任务由数据库与 Worker 保持，不靠模型持续在线。取消只停止未发生步骤；已发生效果按独立补偿执行，补偿失败如实记录。

## 13. 人工审计

覆盖已提交的文本、文件、表单、编辑、确认、拒绝、删除、撤回、配置变化、执行干预和结果反馈。无需记录尚未提交的每次按键；如果产品提供持久化草稿，草稿保存亦需记录。

统一字段：audit_id、operation_id、actor_id、actor_type、occurred_at、received_at、scope、resource/ref、before_revision、after_revision、before/after内容或不可变快照引用、request/task/action、reason_if_provided、result。

失败校验和拒绝同样保留提交及失败原因。密码和 API key 只保存“设置/替换/撤销”的事件，不保留明文历史。所有人工提交的事实与机器修改后确认的内容分别标明作者和确认人。

本机提供操作人切换及本机身份绑定，避免强制恢复复杂账号体系；共用或自报身份明确标为未验证。审计能力不能被描述为已抵抗操作系统管理员篡改；本轮保证应用级追加约束、来源与操作可追踪。

删除对话从普通 UI、检索、摘要、向量/全文索引和 Agent 后续上下文移除，已确认业务记录不随之删除。历史内容继续由审计查询访问；界面删除文案明确该语义，不使用“彻底抹除”。

### 14.1 读取范围

首批对象：Company、Customer、Supplier、Item/UOM、Warehouse、Sales Order 及明细、Purchase Order 及明细、Delivery Note、Sales Invoice、Payment Entry、Work Order、Project、Task。具体字段和子表通过版本化适配清单固定。

增量采用明确时间窗与稳定次键，保存重叠窗口去重，周期全量核对；modified 水位不代表删除捕获。源端删记录只有经过全量身份核对或可靠删除事件才能形成撤销，未覆盖时标注删除检测未验收。

冲突分为身份、字段、单位、关系、时间/状态、源权威和正式设计对实际行为差异。策略按字段与有效期配置，不设置“整个系统永远优先”的粗糙规则。映射改变先重放隔离批次、比较差异，再发布新版本。

未安装薄集成应用时，连接器降为只读，不能通过忽略前置条件放开写入。内部指定负责人不自动等于 ERP 任务已经完成系统分配；外部分配功能若未接入必须单独显示。

## 15. 行业扩展规范

扩展包声明 extension_id、version、platform_api_version、ontology_requirements、connectors、actions、workflows、tests 及可选 UI。由开发端安装/启用，按公司绑定。

本体扩展、源系统适配、动作处理器、流程定义分离。普通流程使用顺序、分支、等待人工/事件、重试和补偿，不引入完整 BPMN 引擎作为首轮依赖。专业优化算法是扩展内部实现。

示例扩展只操作模拟资源，必须显著标为 SIMULATED。验证参数、人工步骤、外部等待、失败、补偿、卸载兼容性。正在运行的动作固定扩展版本；不允许卸载后丢失执行记录。

扩展不可通过配置任意增添 shell/SQL/HTTP 写入能力。注册动作必须有可测试处理器，缺能力返回明确错误。企业范围和审计属于运行必要约束，不扩展成新的安全治理产品。

开发端：公司项目；建模（材料+对话+图）；系统接入。管理端：信息输入；管理助手；企业视图；潜在认识与行动。共用左侧公司/项目选择、独立滚动和当前上下文。初始未发布时允许录入观察，输出调查提示缺模型；正式模型查询不偷偷读取草稿。

## 17. 工程模块与性能约束

在现有 backend/src/enterprise_insight_backend 内渐进拆分：

- storage：四库连接、迁移、仓储、操作回执、备份恢复。
- audit：本地事件、聚合索引、历史查询。
- observations / potential：领域资源及状态。
- tasks：结构化任务、路由、覆盖与结论账本。
- query_gateway：三库检索、图和类型化查询、来源。
- agent_runtime / tool_registry：复用并加入新 Agent、工具和运行阶段。
- actions / management_actions：程序动作与现实行动分离。
- integrations/erpnext：读取适配及 Task 写入回查。
- extensions：注册、版本与示例流程。

api.py 渐进改为按领域 router，不一次重命名整个项目。测试先覆盖领域边界和验收流程，再移除旧入口。禁止为新旧接口复制领域逻辑。

本地 SQLite 使用 WAL、busy timeout、短事务和每库序列化写任务；网络/模型等待期间不持有写事务。记录检索按公司、对象、时间、状态建立索引，不在每次请求重建全量注册表。工具响应有条数与字节上限，读取截断可见。

首轮建议容量验收为 10 万源记录、1 万观察和 5000 模型对象；这是测试目标，不是已证明容量或硬上限。记录机器规格、索引与数据规模，确定性查询目标 p95 不超过 2 秒、任务受理不超过 1 秒（不含模型/外部网络）。预算与进度可见，长任务可取消和续查。未达标先定位索引/查询问题，再决定是否引入额外服务。

默认新实例数据目录放在系统本地应用数据目录，允许显式配置；代码目录不包含实际企业文件、导出、密钥和测试运行数据库。已有目录按迁移清单搬迁，不能直接修改路径造成“数据消失”。开源提交前检查已跟踪文件，不能只依赖 .gitignore。

## 18. 迁移与删减

1. 备份当前实例、统计记录与引用，记录旧 schema 和数据目录。
2. 在新目录建立四库，生成 migration_manifest，保留旧标识或显式映射。
3. 迁移正式模型/发布、源与运行数据；将会议和日常陈述迁观察库。
4. 旧假设/案例没有人工认可证据时进入 LEGACY_UNREVIEWED 候选，不能自动进入 ACCEPTED 潜在库。
5. 原动作调用与日志进入控制库，现实行动进入正式库；含义不明的历史结果保留来源不完整标记。
6. 校验数量、摘要、对象引用、模型版本、对话关联和备份恢复。
7. 进入维护模式切换，原库只读保留回退。新版本产生写入后不能直接回旧库丢弃新数据，必须使用迁移回放或停止回退并修复。

## 20. 协同开发分工

主负责人维护 T02 公共契约、库归属、动作状态和合并验收。并行工作分成有限几条，避免多人修改同一文件：

- 建模/本体/ERPNext 适配。
- 输入/潜在知识。
- 路由/调查/Action。

每组接收接口版本、文件边界、依赖和验收案例；公共 schema 修改由主负责人协调。优先完成一条纵向可用流程再扩覆盖。子任务结束不等于整体验收完成。

### 21.3 模型与性能验收

确定性规则/计算/状态机用独立测试；真实模型用于材料提取、自然语言路由、多轮取证和潜在探索。先固定至少 20 个简单、10 个缺项、10 个复杂任务，并覆盖上表；关键模型任务重复三遍，比较漏项、引用和动作差异。

机械约束场景要求全部通过：未确认不得写潜在认可知识、越范围不得读取、未知外部结果不得盲目重复写、金额/状态与底稿一致。分析质量由人工对证据覆盖、反例、未知表达和方案用途评分，不能用模型自评宣布无幻觉。

报告分别列：单元/契约测试、模拟系统、真实 ERPNext、真实模型、前端用户操作、性能和恢复。任何跳过项写明原因。只用 MOCK 不能通过真实模型验收，只调用 API 不能通过前端验收。

## 22. 最终交付与完成定义

交付程序及一键启动器；四库迁移与一致备份恢复；已固定版本的 ERPNext 测试环境说明；Action 目录/扩展 SDK/薄集成说明；可复现的模拟企业材料和保留操作痕迹；用户手册；需求—代码—接口—前端—测试证据矩阵。

完成条件：四条主业务链全部可用，上述强制约束通过，未实现扩展如实显示，不依靠手工 SQL 或人工调用后端补齐前端缺口。开发过程发现超出本轮的行业需求记录为扩展，不因无限泛化拖延核心交付。

本轮计划交付的是可运行、可核对、可恢复的管理平台。真实管理优化效果必须由后续实施结果验证；程序校验和人工认可都不能替代这种验证。

## 23. 岗位实际工作建模与跨 Agent 一体化

本章由 1.1 引入，1.2 改为虚模专项。新增能力尚未由本文实现；验收记录必须单独标记，不以文档更新代表功能上线。

### 23.1 目标与职责

FDE 先实地考察员工工作，帮助员工使用 AI 或程序提效并验证现场效果，再提交改善后的职责、工作步骤、输入输出、工具、协作、判断、异常和效果材料。平台负责吸收并整理为岗位虚模，引用原企业实模的架构/岗位/流程，不把该批细节直接写入实模。

高层和管理输出 Agent 用这些细节了解企业实际运作，为架构/岗位调整提供依据。管理者决定目标、职责分配和工作指挥；岗位专项不自动把战略拆成员工任务，不派发工作、不考核个人、不擅自调整职责。已有通用 Action 保持原范围，仅在人的明确请求和注册动作条件下使用，不由本专项自动触发。

FDE 的访谈、提效和现场验收由人完成；子 Agent 不通过自由推理填造未观察的细节。建议一个试点项目覆盖同一跨部门流程中的两三个岗位，再扩展。

### 23.2 Agent 组织：四个核心角色加一个建模专用子 Agent

| 参与者 | 输入/职责 | 输出与交接 |
|---|---|---|
| FDE | 现场考察、实际提效，提供适用人员、岗位、时间和证据 | 提交原始材料、已实施做法及效果；人员身份和确认语义分别留痕 |
| 建模 Agent PROJECTION | 管理公司/部门/岗位/流程实模与模型发布 | 启动 WORK_PRACTICE，校验实模引用；不批量合并虚模，单项实模变更走独立流程 |
| WORK_PRACTICE 专用子 Agent | 阅读 FDE 材料、相关实模结构和已知矛盾，精细化岗位活动 | 生成独立版本的虚模及待核实项；不能发布或改写实模 |
| 输入 Agent MANAGEMENT_INPUT | 吸收日常新做法、异常、员工反馈和 FDE 原始陈述 | 复用同一入库服务，写观察、通知相关岗位模型可能过期；不静默改正式模型 |
| 本体 Agent SYSTEM_ONTOLOGY | 将系统账户、单据、字段、程序和实际事件对应到岗位活动 | 提供系统证据、映射及其完整性，不凭一条日志推定完整流程/职责 |
| 输出 Agent MANAGEMENT | 优先查询实模，任务确需岗位细节时读取虚模 | 区分实模结论与虚模补充，报告具体风险；潜在候选仍需人确认 |

WORK_PRACTICE 是独立提示/上下文/评测配置，逻辑上为专用子 Agent，首轮不增加第五个核心 AgentKind 或第二套运行引擎。可从开发端直接启动，其 parent_agent_kind=PROJECTION、profile=WORK_PRACTICE；配置、工具集和父子任务关系留痕。

子 Agent 用独立输入清单避免上下文混杂，必要时继续从 QueryGateway 读取相关正式模型、观察和潜在记录。交接使用 task_id、scope、source_refs、base_release、changeset_id，不依靠别的 Agent 的聊天摘要记忆。

### 23.3 实模锚点与虚模细节，分清岗位定义与工作实例

复用实模中已存在的对象标识作为锚点。虚模新增步骤/关系使用独立标识和 model_kind=VIRTUAL，引用实模节点时保留 typed reference，不通过同名合并。禁止创建平行的“FDE 公司”“FDE 岗位”或另一套身份注册表；虚模中的细分步骤不自动变成实模流程节点。

| 对象/关系 | 含义与约束 |
|---|---|
| Position/Role | 岗位与角色，引用现有部门/架构对象 |
| RoleAssignment | 某人/某角色在某时段担任岗位；人≠岗位，允许代岗和兼岗 |
| Responsibility | 已规定的职责，或明确标为实际承担的职责断言 |
| WorkActivity / 现有 ProcessStep | 可解释的工作活动/步骤，关联岗位和原有流程；存在旧步骤就复用 |
| ProcessVersion | 跨岗位流程的版本和边，不把同一流程复制成多个岗位文档 |
| WorkCase / ActivityEvent | 一次具体工作的案例/事件，用来支持实际做法，不自动推广为全岗位规范 |
| System / Tool / Automation | 现有系统、AI 工具和程序版本，关联辅助/执行/复核步骤 |
| Handoff / depends_on / produces / consumes | 交接、依赖和输入输出，支持多对多；不得强行做成单父树 |

界面按“公司 → 部门 → 岗位”查看实模，用户展开“虚模：现场工作细节”后再显示活动、步骤和案例。底层通过锚点构成关联图，但实模图遍历默认不越过虚模边。跨岗工作在同一虚模版本内保持唯一流程及协作关系，归属不清时待确认。

每项活动可记录：触发、频率、输入、输出、步骤、工具、人工判断点、权限依据、协作者、交接、异常、质量要求、耗时证据和最后现场核实时间。必要字段缺失用 UNKNOWN；不能生成合理但无来源的默认工作步骤。

提效前、试行和当前实施使用版本/有效时间表达，不覆盖历史。AI 辅助与 AI 独立完成分别表示，并保留人的核验角色。一次操作记录无法证明该流程长期如此。

### 23.4 三库归属与可信流转

| 信息 | 首次保存 | 确认后的归属 |
|---|---|---|
| FDE 报告、访谈、跟岗陈述、效果评价及原文 | 观察库，上传原文和 source_hash 保持唯一 | 原文仍留观察库，正式记录引用它，不移动后删除 |
| 岗位实际流程的机器提取 | 观察库虚模资源及提取修订；审阅流程记控制库 | 审阅后成为可供按需读取的虚模版本，仍留观察库，不整体进入正式库 |
| 正式职责/授权的修改 | 控制库变更草稿，关联现行规范和依据 | 有权确认者批准后进入正式库“规范设计”视图 |
| AI 使用情况/程序版本 | FDE 陈述及其细节入虚模，源系统证据入原始导入区 | 系统验证结果可按原规则进入实模运行数据；FDE 解释性关联仍在虚模 |
| ERP 记录与活动事件 | 现有本体导入区和验证流程 | 校验后作为正式运行数据，保留映射和源事件 |
| 低效原因、结构风险或架构调整设想 | 任务候选 | 人确认后进入潜在库，仍区分证据状态 |

“已审阅虚模”只意味着确认在特定范围和时间认可这份现场描述，不意味着批准为制度或使整个虚模成为实模。确认请求包含 confirmation_kind、confirmed_scope、model_kind、record_revision、payload_hash 和人类来源。单项需要进入实模时，重新提交具体断言、业务依据与校验，按实模变更确认；原虚模审阅不作为晋升批准。

人可以否决、修订或撤回。确认人的能力范围由既有操作身份/授权配置检查，不能由 Agent 根据职位名称臆测。自报本机身份按已有审计规则标明验证程度。

### 23.5 字段级证据，防止“有报告所以所有细节都可信”

每个可用虚模版本的职责/活动属性和关系都关联断言（复用现有 Claim/EvidenceReference 结构，持久化遵守分库边界）：model_kind、virtual_model_id、subject_ref、predicate、value/object_ref、assertion_kind、scope、valid_time、source_refs、method、confirmation_ref、revision。已审阅的虚模断言不因此具有实模身份。

assertion_kind 至少区分 NORMATIVE（规定）、OBSERVED_PRACTICE（已核实做法）、SYSTEM_EVENT（系统记录）、REPORTED（陈述）、INFERRED（推断）。统一读取不能去掉该标签。

method 区分 FDE 现场记录、员工陈述、系统测量、规则计算与模型解释。耗时效果必须有样本、期间、计算口径和异常说明；只有“员工感觉快了”时保存评价，不生成提效百分比。样本结果不推广为公司总体节省，也不能直接证明改变由 AI 引起。

同一材料被多个 Agent 转述，source_root_id 相同，不能变成多份独立证据。摘要、新回答和人工确认都不是新的现实测量。缺来源的字段在虚模中只能作为未知/待验证候选，不能显示成已核实；也不能进入实模。虚模属性跨摘要和潜在记录传递时继续保留来源模型类型。

### 23.6 统一查询与更新传播

QueryGateway 增加岗位详情、活动流程、现场证据、前后版本和受影响关系查询，并复用通用公司范围、发布版本、时间和来源校验。

岗位详情默认返回 real_model 的规范/已有正式实际记录/系统证据以及可用虚模的标识等元数据，不默认返回虚模正文。任务显式启用后，增加 virtual_model 分区及其观察来源、潜在依赖、conflicts、coverage 和 risks。虚模数据不能通过模糊的 observed_practice 通用字段混入 real_model。

简单任务如“这个岗位正式流程是什么”只读实模；“FDE 提效后现在具体怎么操作”需要虚模时按第 24 章升级为带来源/风险说明的复杂查询。实模不足时不能悄悄用虚模补齐简单答案；已知过期/矛盾元数据也不能忽略。

复杂任务如“调整这个岗位会影响哪些地方”先查实模依赖，细节确有助于回答时按需展开虚模。复杂任务仍可使用三库相关观察与潜在认识，但不是自动读取全部虚模的授权。推断或虚模路径不能当作已有实模关系返回。

新观察触发岗位/活动的复核提示，不自动改模型。已发布修改通过 outbox 事件通知索引、缓存、相关 QueryManifest 与潜在记录，更新后只复核依赖该内容的结果。已完成报告保留其历史基线，显示当前已过期；运行中任务关键步骤重新校验。

身份合并/岗位退役有版本化别名和继任关系，历史引用保持可解析。跨公司标识、来源不能在迁移/合并时静默改变。

### 23.7 工具与程序检查

岗位子 Agent 可调用 context.read/search、graph.neighborhood 以及 work_practice.read、work_practice.compare、work_practice.propose、work_practice.validate、work_practice.request_review。工具目标固定为虚模资源；复用既有审计/确认协议但不复用实模发布目标。实模变更必须单独调用 change.request，经建模流程处理。

程序必须检查公司与项目范围、对象存在、岗位/人员区分、流程端点、步骤复用、引用版本、来源片段、值与单位、状态、确认范围、并发版本和审计回执。制度与实际差异、审批角色与系统操作账号差异不得强行合并。共享系统账号无法唯一识别人时保留未知。

模型负责材料理解与候选关联。程序校验能阻止越界、无来源字段、失效确认和计算错误，不能凭这些证明材料真实或语义解释绝对正确。验收目标是可核对、可纠错和阻止无依据内容晋升，不宣称零幻觉。

### 23.8 完整示例与验收

FDE 帮助采购员用 AI 整理询价资料，提交实际操作流程、人工复核步骤、用到的系统及少量工作案例。输入服务保存原文一次；岗位子 Agent 引用实模中的采购员岗位和询价流程，在虚模创建细化活动及版本。人工审阅后可按任务使用，但实模没有增加这些现场细节或改变权限。

本体 Agent 将采购系统相关单据/事件映射到这些活动。数据仅覆盖下单时，不推断询价整理过程已被系统全面记录。后续会议提及某次 AI 结果有误，输入端追加同一活动下的观察和复核提示，不覆盖原始案例。

高层问正式职责时只用实模；询问 AI 提效后的工作细节时读取虚模，说明场景/样本限制、来源时间和相关异常。若推测岗位依赖可能变化，作为带虚模来源的潜在候选等待人确认，不因认可便变成实模结论。没有向员工自动派发任何工作。

新增 T05A–T05G 与 U23–U35 是交付的一部分。验收保留 FDE 原始材料、前后流程、确认历史、图中位置和查询结果；检查所有 Agent 在相同模型类型/版本/时间/范围下返回一致的来源与值。实模任务不得通过虚模、摘要或潜在记录的转述绕过该边界。

## 24. 实模优先、虚模按需与风险说明

### 24.1 两类模型与三库是不同维度

实模 REAL 是此前的企业模型，包括组织、正式职责/权限、已确认流程、本体映射及符合正式规则的系统运行记录。仍遵守证据与版本检查，名字不表示绝对无误。

虚模 VIRTUAL 是此次新增的 FDE 现场提效后岗位工作细节，包括工作分解、协作、AI 使用和样本情况。它可以包含真实观察和已审阅内容，不等于捏造，也不专指未来模拟方案；但信息可能局部、短期、受访者片面或被解释错误，因此采用独立模型边界。

正式库保存实模；观察库增加 VirtualWorkModel、VirtualRevision、VirtualNode、VirtualEdge、RealAnchor 与字段证据资源，独立逻辑分区和仓储；潜在库保存人工认可的判断，可引用实模、观察和虚模。控制库记录路由、审阅、调用与风险。保持原三套业务库，不额外增加一个物理业务数据库。

本专项派生出的虚模有独立模型标识，企业/岗位身份仍引用实模注册对象。RealAnchor 标记 real_entity_id、real_release_id、relation_kind、support_ref 和状态；表示解释/细化/对应，不表示虚实对象具有可任意替换的相等身份。

### 24.2 读写和自动化边界

建模 Agent 维护实模及锚点，不默认读取虚模内容；岗位子 Agent 读所需实模并写虚模；输入 Agent 追加现场观察与复核提示；本体 Agent 默认在实模对齐系统数据，针对虚模的事件对应为单独解释性链接；输出 Agent 按任务选择。

虚模节点/边不能参与默认实模图遍历、实模指标聚合、授权推导或业务动作前置条件。虚模中写“经理会看一下”不能产生经理审批权；包含同名对象也不能被默认查询 JOIN 成实模对象。

虚模可以产生建议和候选，但不能独立提供正式业务操作所缺的身份、权限或参数依据。人明确下达操作时，仍走已有 Action 的正式对象、参数与版本校验，且不能以审阅虚模替代对该动作的授权。

### 24.3 路由规则

TaskRoute 增加 model_access=REAL_ONLY 或 REAL_PLUS_VIRTUAL，virtual_reason、requested_virtual_scope、real_gap 和 virtual_revision_refs。默认 REAL_ONLY。

程序按下列顺序处理：

1. 先尝试实模查询和现有确定性工具。实模足够时到此为止。
2. 人明确要求 FDE 现场细节、提效前后实际操作，或结构化任务声明必须的相关细节不在实模时，申请虚模范围。
3. 后端检查任务范围、对应岗位锚点、版本、允许工具和预算，记录启用原因。语义必要性可由模型提出，不能宣称纯规则理解了全部用户意图。
4. 按相关岗位、流程和时间读取，不因是复杂任务就默认扫描全部虚模。范围不足时可继续扩展并更新覆盖记录。
5. 使用虚模的任务标为复杂任务并提供执行/风险说明；实模与虚模均不足时明确未知，不补造。

启用虚模是任务处理方式，不需每次额外弹框问许可；原有潜在保存和动作确认规则仍适用。REAL_ONLY 表示不使用虚模及其派生断言，不表示复杂任务不能按原方案查看普通管理观察/潜在认识；这些数据自身的事实/假设等级继续保留。

对依赖虚模的潜在记录，REAL_ONLY 查询只返回“存在相关虚模依赖资料”的元数据，不把其内容当作绕过限制的入口。用户若明确询问该判断，切换 REAL_PLUS_VIRTUAL 并说明来源。

### 24.4 使用虚模时必须报告的风险

风险说明不是统一一句“仅供参考”，必须关联具体结论，字段至少包括 claim_id、model_revision、source_refs、risk_codes、impact 和 verification_needed。

可由程序检查的风险：样本/时间范围不足、实模锚点过期、无独立来源、提取未审阅、存在未解决冲突、步骤缺失、效果缺计算依据、系统覆盖不完整。Agent 补充解释这些限制会怎样影响当前判断；机器推断的风险也标明推断性质。

回复先说明为什么用了虚模，再区分实模可确定的部分与虚模补充，说明哪些结论若虚模错误会改变，以及建议核实什么。无异常被检出时仍说明这是限于当前覆盖的虚模参考，不能表述为已证明无风险。

示例：“正式模型可确认采购员的职责与审批权限。为回答 AI 提效后的操作过程，额外读取了某次 FDE 现场虚模；该材料只覆盖一个岗位的一段观察期，尚未覆盖异常订单，因此不能据此判断所有采购工作都能按同一方式完成。”

### 24.5 派生依赖与更新

结论账本保存 dependence=REAL_ONLY、VIRTUAL_DEPENDENT 或 MIXED 以及根来源和模型版本；该字段描述模型来源依赖，不替代事实/观察/假设状态。

虚模影响的答案、摘要、缓存、潜在记录和跨 Agent 交接必须保留依赖。人工认可潜在记录不能去掉 VIRTUAL_DEPENDENT。如果后来有独立实模证据，应创建带新依据的修订并明确重新判定，不静默修改旧结论出处。

虚模过期、锚点变更或被撤回时，相关派生内容待复核，失效缓存不进入下一次纯实模任务。实模不会被虚模逆向覆盖；需要更正实模的具体事实走单项提案、依据核对和正式批准，虚模不批量晋升。
