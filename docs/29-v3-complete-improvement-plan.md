# V3 完整改进方案：先把核心能力做成可靠产品

日期：2026-09-06。状态：待实施方案，不是完成声明。

依据：[V3 实现审查](D:/project/palantir/docs/28-v3-implementation-audit-2026-09-05.md)中的 F01–F28，以及保留的 22 组隔离探针。代码基线为当前 `backend/` + `frontend/`；不新造一套并行 V4，也不重写 Companycheck。

开发任务、依赖、交付物和验收编号见配套[实施任务清单](D:/project/palantir/docs/30-v3-improvement-backlog.md)。本文中的新增表、API、工具和状态均为拟实施规范；实施时先核对最新代码，已有合格实现直接复用。

## 1. 产品目标与范围

交付的产品是：**用企业已有的问卷、访谈和资料建立可理解的组织模型；有系统数据时，再把数据对齐到模型；管理层通过图与 Agent 理解企业、探索问题、比较改进方案、记录实际效果。**

两条链共享本体和证据，但有不同正确性要求：

| 工作链 | 输入与输出 | 正确性边界 |
| --- | --- | --- |
| 直观关系 / 可信建模 | 材料、组织职责、流程、系统记录 → 对象、关系、事件、指标 | 程序约束必须满足；来源、口径、版本可验证；不确定项不得自动合并成事实 |
| 潜在关系 / 管理探索 | 管理目标、已知企业模型、现实结果、历史案例 → 机制假设、反例、调整方案 | 允许探索与想象，不要求每个想法先有充分证据；必须标记已知、假设、未知和待验证影响 |

不能承诺 LLM 永远不幻觉、所有映射天然正确、所有经营改善都能被因果证明。工程目标是让错误可发现、结果可追溯、修改可审查、无证据时明确未知，而不是把模型回答包装成绝对正确。

### 本次必须完成

- 无系统数据的企业：从真实格式材料到组织/岗位/职责/权限/流程/各类流动图，支持完整增删改查、Agent 建模、发布与高管查询。
- 有系统数据的企业：文件接入和一个通用只读数据库适配器，完成身份、语义、关系、事件、指标对齐与导出。
- 管理探索：设计侧与结果侧证据、多方案对比、反馈延续、结果与案例积累。
- 三类 Agent 的工具循环、统一 Action/变更集、上下文选择、任务恢复和真实轨迹评测。
- 当前 28 组问题的修复与可复现验收；统一 V3 启动、升级、CI、备份和说明书。

### 明确不纳入本次

- 不替代 ERP/MES 的业务交易执行；首个连接器只读，不向生产系统自动回写。
- 不做所有厂商的专有 ERP 适配器；没有真实系统样本时不把通用接口称为“已适配全部 ERP”。
- 不建微服务、独立图数据库集群或复杂云基础设施；沿用当前本地单体和 SQL 存储。
- 不重新开发问卷系统；Companycheck 等工具导出后导入即可。
- 不做参数训练式飞轮；历史企业以显式案例参考进入 Agent。
- 不新增长篇安全治理、多租户管理页面；保留本地数据隔离、密钥不入库明文日志、项目边界、受控模型发送等基本约束。
- 不把扫描件 OCR、自动因果识别、大规模实时流、万能 SQL/脚本执行列为本次可用能力。接口留扩展点，未实现即明确标注。

## 2. 最终用户流程

### 2.1 无系统数据：先完整做出企业模型

1. 在建设工作台创建公司与项目，通过设置弹窗填入模型配置并测试。公司/项目创建属于建设工作，不要求高管操作。
2. 上传问卷 CSV、访谈 DOCX、文本 PDF、TXT/Markdown 或粘贴访谈内容。预览能看到实际解析文本、表格、公司归属、页码/段落/题号和解析失败项。
3. 若一个问卷导出含多家公司，必须先选择目标公司或明确拆分项目；不根据名称相似度自动混入当前公司。
4. 对投影 Agent 说“根据这些材料建立公司模型，重点看岗位职责、权限与订单流程”。Agent 列出材料覆盖、缺失领域、冲突和建模范围。
5. Agent 生成一份可预览的批量变更集：对象、关系、证据、职责缘由、流程意义、指标与不可量化工作；新增对象用临时引用互相关联。
6. 用户在同一窗口看图与差异，确认或直接说“这个岗位归属不对”。修改的是同一变更集，确认前不会写入正式设计。
7. 批准后程序原子写入并回读结果。显示实际新增/更新/退役数量，不能把生成提案当成已落地。
8. 发布一个明确范围的设计版本。完整性不足可发布“初步模型”，但必须标出范围、未知项与限制；只有非法引用、类型错误、失效变更等硬错误阻断发布。
9. 管理层在使用端直接看模型、问职责与流程、提出改进目标。尚无系统数据不阻断这些能力。

### 2.2 有系统数据：在同一模型上补足现实数据

1. 选择文件数据源或已支持的只读连接器，查看资产、字段、样本与更新时间。
2. 系统本体 Agent 检查已有本体，提出字段含义、身份对应、单位转换、外键关系、指标口径候选；模糊对应进入待确认列表。
3. 预演给出样本命中率、未匹配记录、冲突、字段转换前后值、将新增/更新的对象/边/事件/指标。
4. 批准映射版本与首次同步。后续数据只能按已批准且未漂移的映射产生系统观测，不修改设计基线。
5. 在“设计 / 实际 / 对照”视图查看差异。系统发现的新对象先标记未纳入设计，不能假装已发布组织结构。
6. Agent 按统一指标口径查询或生成可导出的数据集。无需在本产品重建大型 BI 界面。
7. 映射修正后从原始数据重算；重复导入不重复建对象；来源矛盾进入冲突处理而不是最后写入覆盖。

### 2.3 管理目标、探索、行动与学习

1. 管理层提出目标，例如“减少审批耗时，同时保留必要控制”。
2. 管理 Agent 获取当前查询基线、相关组织关系、职责/权限/绩效设计，以及可用的会议与经营结果。
3. 提出多种机制解释与改进方案，分别说明收益、牺牲、受影响角色、反例、需要补充的信息。
4. 用户回答信息请求、补充材料，或指出 Agent 的假设不成立；反馈成为独立记录并保留到下一轮。
5. 方案在隔离图上对比；接受的方案转换为正式变更集。企业外部的实际组织调整由人执行，平台不能把图修改等同于现实已改变。
6. 人录入执行状态、会议结果、绩效或经营观察；有数据源时自动读取已批准口径的观测。
7. 按可比窗口复查。有效、无效、副作用、不足以判断都可积累为案例；只有实际结果支持时才标记效果已观察到。
8. 新公司显式说“参考某公司案例”。参考的是结构化经验与适用条件，不把另一家公司的事实复制成当前企业事实。

## 3. 架构决策：保留单体，统一底层语义

### 3.1 三个工作范围，不增加 Agent 菜单数量

- **PROJECTION：企业投影 Agent。** 服务建设人员，负责材料整理、直观关系建模、职责/权限/流程/指标补全和可审查变更。内部拆为“材料抽象”和“图装配校验”两个阶段，需要时以子调用隔离上下文，不要求用户选择更多 Agent。
- **SYSTEM_ONTOLOGY：系统语义 Agent。** 服务系统接入，负责源结构理解、身份匹配、字段/单位/关系/指标映射及重算检查。不能绕过映射批准或随意执行代码。
- **MANAGEMENT：管理探索 Agent。** 服务高管，解释企业、探索潜在联系、提出方案、记录取舍、请求信息并复查结果。可以广泛思考；正式设计修改必须输出方案/变更请求。

三者共享一个工具注册机制、一个任务执行器和统一数据服务。不是三套数据库，也不是三个互相抄数据的管理系统。

### 3.2 后端模块边界

| 模块 | 负责 | 不负责 |
| --- | --- | --- |
| 本体与投影 | 类型、继承、实体/关系身份、设计版本、图查询、变更应用 | LLM 推理、外部系统读取 |
| 材料与证据 | 文件解析、片段定位、陈述、引用有效性、材料版本 | 把原文陈述自动视为已验证事实 |
| 系统接入与解析 | 源资产、原始记录、映射、身份解析、观测和血缘 | 改写组织设计、决定管理方案 |
| 指标 | 唯一 KPI 定义、目标、口径、观测、单位与时期比较 | 直接推断因果 |
| 管理探索 | 设计/结果信号、假设、信息请求、反馈、方案、取舍和案例 | 绕过可信模型写入流程 |
| Agent 与 Action | 上下文、工具循环、预演/审批/执行、运行轨迹 | 自己维护另一套业务校验 |
| 查询基线与发布 | 模型/数据组合快照、统一查询范围、导出基线 | 把持续更新数据永久冻结在组织模型发布时间 |
| 运行与交付 | 任务队列、迁移、备份、健康、评测、能力清单 | 大型调度/微服务平台 |

实现顺序采用现有文件渐进拆分：先抽取共同服务，再改调用点；不为目录整齐一次性移动所有代码。`api.py` 与 Agent 工具都只调用领域服务，不各自重写规则。

## 4. 统一数据模型与必须保持的不变式

### 4.1 同一对象，设计与现实并存

继续使用 `EntityRow` / `RelationRow` 及参与方表，保留稳定内部 ID。修改其语义：身份不再由 DESIGNED/SYSTEM_BOUND 二选一决定。

- 现有 `properties`、关系参与方等作为当前**设计草稿**的唯一可写来源，所有编辑经领域服务/变更集；发布时形成不可变设计版本。
- 新增 `ObservationAssertion`：现实观察的属性或关系断言，包含对象/关系 ID、字段、值、来源、有效时间、录入序列、批次、映射版本、证据与替代关系。
- 增加 `design_membership = MODELED | UNMODELED` 与明确生命周期。系统新发现但尚未设计的对象只建立待对齐身份与观测，不填造设计字段；不进入正式设计图。
- 对外 `EntityView` 分开返回 `design`、`observed`、`comparison`；兼容期保留旧字段但指明视角。导入程序不再修改 `EntityRow.properties` 和设计参与方。
- 实际关系使用带来源的关系断言，引用统一对象 ID；与设计关系匹配明确后才建立对应关系。系统侧关系变化不会改掉设计端点。
- 没有系统时，访谈中的“公司规定应当如何”和“目前实际如何”也要分开；用户直接陈述可作为人工来源，标记来源类别与确认者，不伪造材料引用。

本次不把所有设计属性改造成通用 EAV 数据库，也不引入全量事件溯源。设计表 + 不可变发布 + 来源观测已经足以支撑当前需求；观察解析的缓存只是可重建读模型。

### 4.2 身份与来源标识

新增 `IdentityBinding`，关键唯一约束：

`(project_id, source_system_id, source_asset_id, source_key)` → `entity_id`。

项目内对象 ID 是唯一身份；显示名不作为唯一键。相同编码属于不同系统时不能自动认定同物。来源复合主键先做规范序列化，保留原始值；映射键变更必须版本化。

匹配顺序固定为：已批准绑定 → 该资产已批准的精确业务键规则 → 候选匹配 → 人确认。名称、模糊相似度、模型判断只能产生候选。

跨项目不自动共享对象 ID；本轮保留项目隔离。跨项目参考或合并通过明确导入/映射完成，不暗中把同一家公司的不同项目合并成一个库。

### 4.3 来源权威与冲突

- `authority_priority` 明确定义为“数字越大优先级越高”，默认 100；按目标字段/关系分别配置，而非整套 ERP 永远压过所有来源。
- 先过滤错误类型、无效时间、撤销来源、未批准映射和未解决身份，再比较优先级。
- 同来源同业务记录的后续修订替代前版；不同来源同优先级且值不同，产生 `UNRESOLVED_CONFLICT`，不能按导入顺序定胜负。
- 人工裁决是有范围、有效期、原因的解析决策，不悄悄修改源数据。
- 解析结果返回选中值、候选值、来源、规则版本与冲突状态。单独缓存 `ResolvedObservation`，唯一键包括对象/字段、查询时间、数据截止序列、解析策略版本。

### 4.4 一个 KPI 身份，两种存储职责

保留 `MetricDefinitionRow`，新增非空唯一 `metric_entity_id` 指向图中的 METRIC 实体，形成一对一扩展。名称与图上战略/岗位关系不在两处独立写；`owner_entity_id` 等旧便捷字段过渡为统一服务生成的只读投影。

指标定义需要：类型、单位、币种（适用时）、统计方向、聚合方法、粒度、周期及时区、统计范围/维度、目标规则、适用时期、口径版本、证据。没有这些信息可保留为待完善 KPI，但不能参与数值达标或跨指标比较。

观测保存：定义版本、`period_start/end`、业务时区、维度键、数值/定性值、来源、业务记录键、修订序号、录入序列、质量标志、证据。

- 原始观测可以多来源多修订；每个“指标定义版本 + 时期 + 维度”只能有一个已解析有效结果，或明确的冲突状态。
- 修改目标、口径不回写历史；人工 `status` 与程序计算的 `computed_status` 分开，冲突必须可见。
- 同周期三条修订不算三期。缺失期、未达标期、不可比期分别表达。
- 不同币种/单位、范围或非重叠时期不能直接比较。显式转换须记录汇率/系数来源与有效期。
- 金额与高精度计量使用十进制值与明确精度/舍入规则，不能以二进制浮点近似值作为金额核对真值；百分比统一规范单位，缺失不填零，分母为零返回不可计算及原因。

### 4.5 本体与引用约束

- 日期、时间、UUID、数值范围、枚举、必填项真实解析；不再仅检查字符串。
- 子类型递归继承属性和角色约束；禁止继承环；不兼容覆盖拒绝。关系端点判定支持合法子类型。
- 同一验证器用于手工、Agent、导入、批量变更和方案应用。正常创建/发布强类型对象仍校验必填项；未建模来源记录不冒充合格设计对象。
- 退役端点不能创建新有效关系；退役操作预览受影响关系，必须显式选择同批退役或改接。
- 引用验证材料/片段存在、项目归属、定位和撤销状态；无证据声明只能标“人工确认/待核实”，不能填随机 ID。
- PATCH 未提供字段保持原值；null 仅允许清空可空字段；数组只有显式提交才替换；更新合并已有数据后验证整体状态。
- 乐观锁使用数据库条件更新 `WHERE revision = expected_revision` 并检查影响行数，不能只在 Python 里先读后比。
- JSON 扩展字段必须对应版本化 schema；保留类型如因果假设不能通过通用弱校验入口写入。

### 4.6 主要存储变更清单

| 现有/拟新增结构 | 本次用途 | 唯一性/版本要求 |
| --- | --- | --- |
| Entity / Relation / Participant（修改） | 同一身份与设计草稿 | 项目隔离、修订锁、设计/现实分离 |
| IdentityBinding（新增） | 来源编码对应统一 ID | 项目+来源+资产+原始主键唯一 |
| ObservationAssertion（新增） | 多来源属性/关系现实断言 | 来源记录+映射版本+输出键幂等；不可变历史 |
| ResolutionDecision / ResolvedObservation（新增） | 裁决记录与可重建当前读模型 | 策略版本、有效期、冲突显式 |
| SourceAsset / RawBatch / RawRecord（新增） | 稳定资产、不可变原始批次和逐记录定位 | 文件名非资产身份；原始批次与处理任务分离 |
| MappingVersion / MaterializationRun（新增） | 已批准映射、重算与同步结果 | 批次+映射+解析策略+解析器版本幂等 |
| MetricDefinition / Observation（修改） | 唯一 KPI 图实体扩展与时序修订 | 图指标一对一；观测来源版本化 |
| Publication / QuerySnapshot（扩展/新增） | 设计发布与模型/数据组合基线 | 不可变 manifest/hash，不混入最新草稿 |
| AgentRun / AgentStep（扩展/新增） | 持久执行计划、工具结果、租约、重试 | run+step+call 唯一；输入/输出版本可回放 |
| Action / ChangeSet（修改） | 共用工具定义，审批与原子应用 | 输入哈希、预演哈希、基线和定义版本绑定 |
| ManagementInsight / InsightOccurrence（修改/新增） | 稳定问题身份与每轮结果 | 问题指纹稳定；每轮只新增 occurrence |
| InsightEvidenceLink / Feedback（新增/复用） | 多对多证据和管理反馈 | 支持/反对/未知角色，反馈不可被下一轮覆盖 |
| Scenario / Case / Evaluation（修改） | 基线方案、效果案例、真实轨迹评测 | 都引用明确运行/基线，不依赖自报计数 |

每张新增表必须随所属功能一起带迁移和测试；不提前铺一堆尚无消费者的表。材料大文件与原始批次保存在数据目录，数据库保存定位、校验与可检索内容，不把整批文件永久塞进预览 JSON。

## 5. 查询、发布和上下文：模型不混版，数据可更新

统一 QueryScope：

```text
project_id
model: release_id OR draft_revision        # 必须二选一
view: DESIGN | OBSERVED | COMPARE | SCENARIO
data_snapshot_id                          # 本次已提交数据集合/截止序列
valid_at / observation_window             # 业务时间，不等于导入时间
scenario_id?                              # 仅方案视图可用
include_unconfirmed_material: boolean
selected_material_version_ids[]
reference_case_version_ids[]
```

服务创建不可变 `query_snapshot_id`，解析“最新”指针为具体版本。图、Agent 工具、分析、导出都传这个 ID，禁止各自再取最新数据。

- 高管默认使用最新发布模型 + 创建查询时的最新已提交数据。数据更新不要求重新发布组织模型；界面同时标出“设计版本”和“数据截至时间”。
- 没接系统时也能创建数据快照，集合里可以只有访谈、会议、人工观测，甚至为空。
- 建设端可以选草稿，但开 run 时固定草稿修订。运行途中有更新，提示基线过期并让写操作重验，不无声换上下文。
- 方案固定自己的基线模型和数据快照；历史导出使用整个原快照，不只固定图。
- 设计发布包含本体版本、对象/关系、指标定义/目标口径、模型证据版本和范围说明；业务观测以独立数据快照查询。
- 使用录入截止序列与业务有效时间处理迟到/修正数据，保证旧报告仍可回放。新快照可以包含对历史时期的修订，必须标示修订来源。

材料检索优先级：当前消息 → 用户选中的材料 → 本轮相关实体/片段 → 近期必要对话 → 显式历史案例。工具描述与用户目标单独保留，不与大型图 JSON 一起硬截断。输入过大时分块检索、生成带来源摘要并继续，不静默丢弃附件。没有读到的材料不得声称已读。

## 6. 材料导入与原始数据处理

### 6.1 支持格式与能力声明

一次完成 CSV/问卷 CSV、TXT/Markdown、DOCX 段落与表格、文本 PDF、XLSX 工作表、明确 schema 的 JSON。实现每个解析器之前，对应能力为 unavailable，前端不得列成可用。

扫描 PDF 返回 `OCR_REQUIRED` 或 mixed-content 警告，不把空文本判成功。XLSX 公式不执行，使用文件已有缓存值并标记不可得情况。宏、嵌入对象、密码文档等明确拒绝/提示；不是把所有 Office 特性都算支持。

所有解析器输出统一 `ParsedDocument`：文本片段、表格/行列、定位、检测编码、解析版本、覆盖/失败统计。文档材料与系统原始表共用解析器，但后续走不同领域处理，不能仅因 CSV 就假设是问卷。

### 6.2 生命周期与幂等

预览状态：`UPLOADED → PARSED → READY_TO_CONFIRM → CONFIRMED`，另有 `FAILED / EXPIRED / REJECTED`。确认绑定文件 hash、解析器版本、目标公司/项目和预览 schema；输入变化需重新预览。

原始材料去重仅表示内容已保存，不代表映射已经完成。物化任务另行以 `(project, source_asset, raw_batch, mapping_version, resolver_version, parser_version)` 幂等；同文件换映射允许重算。

逐记录结果固定为：`CREATED / UPDATED / UNCHANGED / CONFLICT / QUARANTINED / EVIDENCE_ONLY`。任务整体不得把零物化记录标为“已写入全部企业对象”。有效记录、隔离记录和未知字段可导出核对。

预览允许过期清理，但已确认源文件、片段、行定位和血缘不能跟着删除。撤销材料时保留引用墓碑，标记受影响的模型/分析需复核；不会直接让历史报告的证据链接变成不存在。

### 6.3 原始系统摄取与重算

采用“解析 → 原始批次 → 预演 → 批次写入待提交观测 → 核对 → 发布数据快照”。大文件分批写，任务全部完成前不把半批数据当成完整最新快照。错误策略默认隔离并阻止默认发布；用户可显式接受部分批次，快照永久记录缺失范围。

映射修正产生新输出版本，旧输出按源记录/输出身份被替代；删除映射或源记录缺失不等于实体退役。只有来源提供显式删除/失效语义且规则获批，才可结束该来源观测的有效期。

单位、日期、枚举、外键查找和受控聚合通过注册转换算子完成；算子有版本、输入输出类型和示例。Agent 不能生成任意脚本执行。材料解析或转换失败必须有明确错误代码与行定位。

## 7. Agent：从单次回答升级为可恢复的任务执行

### 7.1 一个工具定义贯通所有入口

`ToolSpec` 包含：`key/version`、允许的 Agent 范围、输入/输出 schema、只读/草稿/正式写入类别、审批策略、预演、执行、补偿能力、超时、幂等规则、受影响资源类别和测试入口。

同一注册表生成 Agent 可见工具、后端能力清单、Action 可执行判断和前端按钮状态。没有 handler、输入校验或测试的工具不可声明为可执行。现有白名单转为注册表中的工作范围限制，不由模型决定自己有哪些权力。

至少实现的工具族如下；点号命名是拟定注册键，不代表这些工具目前已经实现：

| 工具族 | 主要能力 | 使用范围 |
| --- | --- | --- |
| `context.describe / materials.search / materials.read / evidence.resolve` | 当前基线、覆盖情况、材料检索、片段定位 | 三类 Agent |
| `ontology.list / ontology.validate / graph.query / graph.neighbors` | 类型与约束、局部图、多方关系、有效对象查询 | 三类 Agent；管理侧固定查询基线 |
| `changes.create / changes.update / changes.preview / changes.validate` | 生成/修订统一变更集 | 投影；系统仅映射/系统模型范围；管理仅方案草稿 |
| `changes.apply / projection.readback` | 批准后原子应用并核对 | 执行器按已批准调用执行；Agent 不能自行批准 |
| `metrics.define / metrics.update / metrics.observe / metrics.query` | 唯一 KPI、观测与可比较数据 | 投影维护设计定义；系统写来源观测；管理可提交人工观测 |
| `sources.describe / sources.sample / mappings.propose / mappings.preview` | 资产检视、字段含义、身份和转换候选 | 系统语义 Agent |
| `mappings.approve / materialization.run / materialization.inspect` | 批准与同步/重算状态 | 人工批准后执行；只读运行可按既有授权重跑 |
| `hypotheses.save / hypotheses.revise / hypotheses.feedback` | 机制、反例、未知项与管理层反馈 | 管理 Agent |
| `information.request / information.answer / meetings.record / meetings.update` | 信息补充、会议结果、行动状态 | 管理 Agent，投影可请求建模信息 |
| `analysis.run / insights.read / insights.review / tradeoffs.record / tradeoffs.update` | 设计/现实对照、意见和取舍 | 管理 Agent |
| `scenarios.create / scenarios.edit / scenarios.compare / scenarios.to_changes` | 隔离图方案与批准落地请求 | 管理 Agent；正式应用仍走统一变更 |
| `actions.observe / cases.search / cases.reference / cases.propose / cases.revise` | 现实结果和显式案例参考 | 管理 Agent；投影可参考已批准结构模式 |
| `datasets.plan / datasets.preview / datasets.export` | 受控语义查询和数据导出 | 系统和管理 Agent |

用户可直接说修改对象、回答请求、更新指标或删除错误关系；不要求记工具名。用户聊天内容与上传材料只作为任务输入和证据，不得被当作新的系统指令。

### 7.2 持久化执行流程

任务生命周期：`QUEUED → RUNNING → WAITING_USER / WAITING_APPROVAL → RUNNING → SUCCEEDED`，另有 `FAILED / CANCELLED / BUDGET_EXHAUSTED`。沿用/兼容原有阶段标签作为子状态，不让界面把“模型返回”误认为“业务完成”。

每个 `AgentStep` 保存工具版本、输入、基线、调用 ID、结果、错误、模型/提示版本、耗时和可见进度。工具返回实体 ID 后，下一步才以实际 ID 查询/建边；没有调用结果不得编造“已成功”。

执行机制：读取固定基线 → 模型提出下一步 → 程序验证工具和输入 → 执行只读/草稿操作 → 结果回传 → 继续或等人批准 → 正式写入 → 回读核对 → 总结。结构化输出无效时允许有限次纠正，仍失败则显式失败，不能退化为普通文本却声称动作成功。

默认可配置预算：最多 12 轮模型交互、40 次工具调用、15 分钟单次运行墙钟预算；单次外部模型调用默认 90 秒超时、最多 2 次有退避重试。到达限制保存检查点与未完成项，由用户继续；不截掉第 21 个动作。用户审批等待不占活动运行时间。请求预算不等同费用上限；只有提供方返回用量且配置价格可核对时才展示成本估算，否则显示未知。

同一对话按消息接受顺序执行；发送新消息可排队或明确取消前任务，不能让未来消息污染旧任务历史。项目/工作范围固定在会话上，切换公司后不会自动复用旧公司的会话。

### 7.3 批量变更与 Action 语义

保留现有 ChangeSet 与 Action，不再增加另一套“提案写入引擎”。ChangeSet 表示业务操作集合；Action 表示一次批准执行的调用与结果。两者共用预演和应用逻辑。

- 临时引用使用显式字段，例如 `{"ref":"tmp:role-sales"}`；仅接受同变更集已声明的临时键。预演预分配固定 UUID，验证依赖，展示实际将写入的最终图。
- 新增、改名、属性变化、关系参与方变化、退役可以同批提交；预演只保存草稿/检查报告，不改变设计或已提交观测。
- 批准令牌绑定输入 hash、工具版本、变更集版本、预演 hash、对象修订和基线；任一变化则返回 409 `APPROVAL_STALE`，必须重演。
- 本地数据库内的设计批量变更采用单事务全成全败，成功后再回读；不得每条操作自行 commit。
- 单个 HTTP 请求重试、前端重复点击和 Worker 重领使用同一个业务幂等键，不重复写。
- 回滚是受修订检查约束的补偿操作，不能用当前最新修订强制退役已被别人编辑的对象；不支持补偿的类型不显示通用回滚按钮。
- 审批状态、工具执行结果、业务效果三者分离：模型生成、数据库应用、现实企业调整不是同一件事。

### 7.4 Worker 最小可靠实现

前端仅提交/取消/继续任务并订阅或轮询，不主动再调“立即执行”。数据库队列是唯一执行入口。

- 原子条件领取，保存 owner、lease、heartbeat、attempt；只恢复过期租约。
- 模型网络请求不占用数据库写事务；短事务提交步骤结果，工具效果和步骤状态采用一致的幂等策略。
- 每个任务异常隔离，失败事务 rollback 后用新事务记录错误；单任务失败不停止工作循环。
- 关闭进程时停止接单、保留检查点。未知结果的外部调用不得无脑重放；本轮没有业务系统写回。
- 不承诺所有外部调用 exactly-once；本地持久效果以唯一约束和幂等保证。

### 7.5 聊天删除与痕迹

支持会话新建、重命名、搜索、删除、恢复和明确确认的永久清空。运行中删除先取消/停止后续模型发送。聊天中已确认的企业对象、关系、信息回答和案例不随聊天清空；业务记录保存独立、最小化的来源/确认信息，不用聊天作为唯一数据载体。

上下文只包含未删除且在任务时间范围内的消息。用户清空历史后不把旧摘要偷偷带回；若已有业务事实来自先前确认，Agent 应从企业模型读取并标明来源，而不是冒充记得被删除对话。

## 8. 系统接入：先完成一个可验收的纵向样板

### 8.1 连接器协议

定义 `test / capabilities / list_assets / describe_asset / sample / read_page / checkpoint`，使用受控表/视图与只读连接。首个网络数据库适配器计划为 PostgreSQL 表/视图读取；开发验收使用本地合成业务库。选择它是明确的本轮实现边界，不表示用户的 ERP 一定使用该数据库。

不具备对应驱动或网络环境时能力显示 unavailable，不能以文件源 MOCK 测试冒充真实连接器成功。后续 ERP/MES 厂商适配按同协议增加；实际接口、编码、增量字段、删除语义需有样本/文档才能承诺兼容。

同步默认手动触发；可配置本地间隔任务属于后续同模块能力，不依赖操作系统 cron。增量以 `(更新时间, 主键)` 组合游标避免相同时间戳漏行，支持明确的重叠回读与幂等；源无可靠增量字段时使用全量批次核对并标示限制。

### 8.2 映射和数据查询

映射版本包含稳定资产 ID、列选择、语义说明、身份规则、实体属性、关系参与方、事件时间、指标口径、转换算子、范围筛选、权威规则。状态为 `DRAFT → VALIDATED → APPROVED → SUPERSEDED / DISABLED`，只有 APPROVED 可正式物化。

外键对齐使用 IdentityBinding；引用未解析时隔离关系，不创建猜测实体。转换校验同时检查字段类型、单位、空值、枚举、重复键、业务时间和数据覆盖率。源 schema 漂移时暂停受影响映射，要求重演；无关新增列可按显式兼容规则忽略。

数据导出工具接受类型化查询计划：对象类型、属性、允许的关系连接路径、过滤、分组、已注册指标、时间范围。只沿本体和映射许可的连接，不让 LLM 自由生成任意 SQL。每份结果附单位、数据截至、覆盖/冲突数量和来源，预览与导出同一基线。

### 8.3 首个样板：订单到回款

用合成 ERP 的客户/订单和财务的发票/回款、生产的工单/发货三组源记录演示：异码同客户、同码异客户、订单—工单—发货—发票—回款联系、跨期回款、缺少外键、来源冲突。

样板验收不仅是“有数据进库”，还要求：图中角色/流程能找到对应订单等运行对象；可导出订单履行和回款数据；不能通过重复连接造成金额翻倍；分摊与多对多关系有明确规则；缺失数据不得被自动填零或当作无业务。

## 9. 管理探索：同时理解设计逻辑和现实结果

### 9.1 补足岗位、流程与绩效的设计内容

本体默认模板增加下列可扩展结构，保留自由文本解释和证据，不强迫用户逐字段填表：

| 设计对象 | 需要表达 |
| --- | --- |
| 战略 | 目标、优先级、约束、期间、成功标准、不可牺牲项 |
| 岗位/职责 | 存在目的、预期产出、责任边界、为什么这样分工、依赖知识/能力、替代条件 |
| 权限 | 决策事项、授权来源、适用范围、金额/业务条件、委托/升级路径、实际承担责任者 |
| 流程/活动 | 触发、输入/输出、负责人、参与者、信息/资金/物流/指令路径、必要性、交接与异常处理 |
| 绩效契约 | 考核对象、具体指标/定性项、权重/门槛、可控程度、数据可得性、激励规则、战略关联 |
| 设计取舍 | 目标间冲突、接受的损失、谁获益/承担成本、成立条件、代价上限、复查指标 |
| 不可量化工作 | 为什么难以量化、可采用的定性证据、复核方式与频率，不伪造数值指标 |

这些用于提出管理问题和方案，不代表“缺任一字段企业就有问题”。资料缺失必须与设计缺失分开，低覆盖时先说明盲区。

### 9.2 潜在联系的探索方法

管理 Agent 围绕用户目标开展自由探索，至少能从目的与约束、责任与权力、局部与整体激励、知识/能力依赖、非正式协调、风险耦合、交接成本和不可量化工作等角度提出方案；角度是可增删的提示模块，不是强制规则清单。

拟定 `ExplorationModule` 扩展协议：模块 ID/版本、适用目标、提示片段、所需上下文类别、可选结构化输出 schema、评测案例。新增研究方向不改主执行器；不允许模块替换证据事实或升级工具权限。

输出分层：先给管理者可理解的解释和多个方案，再提供结构化记录。最小记录包含主题、机制假设、涉及对象、已知支持、反例/替代解释、未知项、可能收益/牺牲、验证办法。没有足够证据的有用想法仍可保存为 EXPLORING；不要求每条潜在关系必须能被现有规则打分。

### 9.3 现实结果输入与印证

结果来源包含会议纪要中的明确事件/问题/行动状态、绩效记录、经营结果、人工观察和已接入系统事件。周期会议反复出现同一主题本身不是异常；要区分正常复盘与持续未解决问题。

规则只负责可计算信号，如可比时期的未达标、明确超时、责任/权限结构约束；Agent 可基于所有可访问材料另提规则未覆盖的假设。

| 证据组合 | 系统表达 |
| --- | --- |
| 有设计风险、暂无可用现实结果 | STRUCTURAL_WARNING：结构可能有问题，结果未知 |
| 有结果异常、暂无对应设计解释 | UNEXPLAINED_ANOMALY：现实异常，原因待探索 |
| 两侧相关且可比、有共同机制的支持 | CORROBORATED：相互支持，仍不等于因果已证明 |
| 存在明确相反方向证据 | EVIDENCE_CONFLICT：并列展示，不能只取最大分数 |
| 已接受取舍且尚在约定边界内 | ACCEPTED_TRADEOFF：保留成本及监测，不当成已消失 |
| 已接受代价越界/前提失效 | TRADEOFF_REVIEW_REQUIRED：重新审议 |
| 没有足够信息判断 | INSUFFICIENT_EVIDENCE：不以缺失当作正常或异常 |

支持/反对记录多对多连接设计风险和结果信号，附匹配依据、实体、机制与时期；同一结果可以关联多个假设，不能被第一个匹配消耗。共享顶层战略不自动表示相互印证。

显示“证据充分性、覆盖范围、严重程度、需确认事项”，不展示未校准的 98% 正确率。用户给出的经验判断可以保留，但须标注人为判断，不能被规则自动当作统计置信度。

### 9.4 问题身份、反馈和复查

问题稳定指纹由项目、机制/问题键、规范化受影响对象与指标范围组成，不含标题或本轮 run_id；标题改变不新建问题。语义相近但不能确定相同的问题由 Agent 提议关联/合并，程序不做无依据模糊合并。

`ManagementInsight` 保存稳定状态和管理意见；`InsightOccurrence` 保存某轮基线、信号、分类与差异。反馈和决定追加版本，当前状态是它们的投影。

- 相同输入/证据不重复创建 OPEN 项；否定与取舍下轮保留。
- 新证据、模型变更或规则版本导致变化时新增 occurrence。达到该问题显式重审条件才重新打开，并展示原因。
- 一轮未再检测到不能自动判已解决；要有结果、观察窗口和管理确认。
- 信息请求回答后形成独立回答/证据记录，可再改、撤销、追问，并触发显式的重分析，不偷偷删历史。

## 10. 方案、因果、行动与案例

### 10.1 真正可看的方案

Scenario 绑定模型发布/草稿修订与数据快照，overlay 使用同一 ChangeOperation schema。支持新增/修改/退役对象、重接关系、调整职责/权限/绩效设置；查询在固定基线副本上应用 overlay。

方案图与正式图分开；提供对象/边增删改差异和受影响岗位/流程清单。可同时比较至少两个方案。方案基线过期时重基并显示冲突，不能直接写正式模型。

### 10.2 因果能力边界

本次做可证伪假设与干预记录：干预是什么、预期机制、结果变量、可能混杂因素、对照/前后时期、滞后、数据需求和反证条件。允许结构化因果图表达想法，但不把箭头当成已证明的因果。

有合适数据时展示可复算的前后对比或已注册分析方法，必须标注适用条件和限制。复杂因果估计作为后续可插拔分析器，不以 LLM 数字回答冒充统计结论。

### 10.3 实际行动及效果

平台 Action 成功只意味着数据或流程记录已处理。现实行动单独记录负责人、计划、开始/完成状态、外部完成凭据、预计/实际影响和复查日期。管理者确认组织调整已执行后，才新增现实观察；设计变更不会自动改变 OBSERVED 视图。

ActionObservation 与 MetricObservation 使用同一指标身份、时期和证据，不再维护另一套无法分析的效果数字。定性效果可以记录为定性观察。

### 10.4 简单有效的案例积累

案例由企业情境、问题与机制、干预/方案、执行记录、结果/副作用、失败教训、适用与不适用条件组成。保留病例版本及证据。尚无结果的案例标“方案参考”，不能标“已验证成功经验”。

支持 Agent 从已确认问题/行动生成案例草稿、用户修改和确认、显式指定案例参考。跨公司引用只是先验建议；目标企业仍要调研、核对适用条件。无需额外飞轮平台、自动训练或无条件复制模板。

## 11. 前端只做必要入口和可操作结果

保留同一应用中可切换的建设/使用模式，不另做两套业务内核：

| 模式 | 常用界面 | 轻量附属操作 |
| --- | --- | --- |
| 建设工作台 | 公司/项目选择；建模工作台（材料、聊天、图）；可选的数据接入 | 模型设置弹窗、变更确认抽屉、发布按钮、高级工具折叠区 |
| 管理使用端 | 企业全景；管理 Agent | 方案对照、待回答/待确认、行动与结果卡片，均从对话或图打开 |

公司/项目创建放在建设模式；企业模型与图必须也能在使用模式查看。已有 `/developer`、`/executive` 路径保持兼容，默认项目与查询模式来自统一路由状态；侧栏选择更新 URL，不能由旧 URL 强制跳回旧项目。

### 必须具备的交互

- 聊天窗口提供材料拖入/选择、任务阶段、实际已读材料、待确认变更、运行取消/继续和错误重试；模型尚未配置时就地引导设置。
- 结果卡片支持相关 CRUD：编辑对象、增删关系参与方、修改指标、回答请求、补充会议、确认/否定假设、更新取舍和效果。复杂 schema 由本体驱动表单，不要求用户编辑 JSON。
- 图按组织层级分组、按岗位/流程聚焦、搜索定位、展开邻居；资金/信息/物流/指令等关系可按层切换。多参与方关系以关系节点呈现，保留角色标签，不截成任意两端。
- 潜在关系用独立、默认不混入事实图的假设覆盖层，可点击看机制与证据。设计/实际/对照/方案有明显标识。
- 选择一个对象能看“它是什么、为什么存在、做什么、由谁决定、与谁相连、如何考核、信息从哪里来”。
- 默认不渲染整个大企业全图；首屏聚合，局部展开，避免不可读的毛线图。
- 前端只发用户真正编辑的字段；不得初始化空 evidence/feedback 再覆盖原值。输入组件与 API 参数共用生成类型和统一校验消息。
- 业务响应提供 `changed_resources`，统一触发图、指标、问题、案例和项目修订缓存失效；不能只刷新 Action 列表。
- 异步任务用有游标的轮询先做可靠版本，活动任务约 2 秒刷新，终态停止；是否增加 SSE 后续以实际需要决定，不成为本次前置依赖。

前端无需建设“每个底层表一个页面”。但所有用户必须完成的操作都要通过 Agent 或结果卡片可达；API 存在而使用者无法完成，不算交付。

## 12. 前后端契约与协作规则

### 12.1 契约唯一来源

后端可执行 Pydantic schema 和路由生成 OpenAPI，提交到现有 `contracts/openapi.json`；前端类型和客户端从它生成。契约文件不再手工维护第二套业务含义。破坏性变化本次优先通过新增字段/适配层过渡，仍使用 `/api/v3`，不同时运行两套语义不同的同名接口。

所有资源携带 ID、项目、修订；写入要求 `expected_revision`（创建除外）与适用的幂等键。异步受理返回 202 与 `job_id/run_id`，不是业务成功。错误统一包含 `code/message/field_path/details/retryable/request_id`，前端展示人能理解的信息。

主要错误码：`REFERENCE_INVALID`、`ONTOLOGY_VALIDATION_FAILED`、`REVISION_CONFLICT`、`APPROVAL_STALE`、`SCHEMA_DRIFT`、`IMPORT_KIND_UNAVAILABLE`、`MAPPING_NOT_APPROVED`、`IDENTITY_AMBIGUOUS`、`EVIDENCE_WITHDRAWN`、`INSUFFICIENT_COMPARABLE_DATA`。校验错误用 422，修订/审批/状态冲突用 409；不能以通用 500 处理已知输入问题。

### 12.2 API 交付组（均以 `/api/v3` 为前缀）

以下列出拟保留/扩展的契约族，实施 T01 产出精确 OpenAPI 操作清单；对现有同义路由优先扩展而不是再造重复接口。

| 契约族 | 拟定操作/返回 | 最小前端消费者 |

| capabilities / model-profiles | GET 能力；配置 CRUD、测试、默认选择；仅返回脱敏连接信息 | 模型弹窗、文件选择器、Agent 范围选择 |

### 12.3 两个开发窗口的职责

- 后端负责领域不变式、数据模型、迁移、OpenAPI、工具注册、任务执行和接口验收。
- 前端负责可达入口、聊天与结果操作、图交互、状态一致性、生成客户端和浏览器验收。
- 指定后端窗口作为契约合并责任方；前端提出契约需求但不手改生成 schema。约定变更以接口示例、错误示例、验收步骤和迁移说明交接。
- 可用 MOCK 做前端先行开发，但合并前必须切真实后端验收，MOCK 通过不能关闭工作项。
- 每批只允许一个任务修改共享 `models.py/schemas.py/api.py/迁移链`；其他任务开发各自服务或测试后顺序合并。未经用户要求不新建或派发其他任务，本轮仅明确分工。

## 13. 迁移、清理、运行与性能

### 13.1 迁移原则

过去曾允许删除数据不等于本轮计划授权清空现有数据。本方案默认保留；不可恢复的旧覆盖结果必须标记来源不明，不能猜回原设计。

实施采用 expand → backfill → validate → switch → contract：

1. 保存本机一致性备份，盘点 schema/version/行数/文件校验；备份属于私有运行数据，不提交 Git。
2. 识别已知旧版本或无版本 schema 的结构指纹；只有完全匹配某已知 schema 才标记相应起点再顺序升级。未知结构停止并出报告，绝不 `create_all + stamp head`。
3. 添加新字段/表，不先删除旧字段。将原设计、系统来源、KPI、问题反馈等迁入对应结构，生成逐项映射报告。
4. 原 `DESIGNED` 记录保留为设计；`SYSTEM_BOUND` 有可验证来源的转现实观测，无证据的标 `LEGACY_UNRESOLVED`，不自动覆盖设计。混合来源无法拆解时进入待复核。
5. KPI 先匹配明确现存 ID/引用；无法一对一对应时出迁移候选，不能仅按同名合并。重复洞察按高确定性键归并；冲突反馈全部保留。
6. 历史发布缺少当时本体/指标/数据快照时，标 `PARTIAL_LEGACY_SNAPSHOT`；保留原图，但不能填当前数据伪装成完整历史版本。
7. 回填核对通过后切换读写服务；过渡期所有入口经同一适配器，禁止两个独立双写服务各自维护真值。
8. 新建和升级用相同最终 schema 测试。旧字段/旧 V2 清理在新路径验收后单独列删除清单，届时按明确范围执行；本轮不删除。

迁移按逻辑命名为 `scope-and-provenance`、`metrics-unification`、`agent-runtime`、`insight-lifecycle`、`scenario-and-package`，实际 Alembic revision 由实施生成，不在计划中伪造版本 ID。数据库回退以停机恢复已核验备份为主，不承诺每个结构变更都能无损 downgrade。

### 13.2 数据导出、移交和备份

分清三类用户产物：

- **分析数据集**：CSV/XLSX/JSON，固定查询基线、字段口径和来源，供其他软件使用。
- **案例包**：跨公司显式参考的情境/模型模式/效果和适用条件，不默认包含整个企业原始材料。
- **项目恢复包**：版本化 manifest、对象/边、本体、材料/证据、观测、映射、发布、问题/反馈、会话（未清空部分）、动作/观察、方案和案例；默认排除 API 密钥/连接密码，恢复后重新配置。

另有用于本机升级灾难恢复的数据库和数据目录一致性备份，它可能含原有连接配置/加密数据，不等同可分享项目包。运行中的 SQLite 不直接复制一个 `.db` 文件当作完整备份，须按一致性备份流程处理数据库及其所引用的不可变文件。

项目恢复默认导入为新项目，保留包内 ID 对照；不覆盖现有项目。合并必须额外预演，显示身份/版本冲突。先校验版本、hash、依赖和资源数量，再在暂存环境恢复并核对，最后切换可见；失败不留下半成品项目。压缩包路径限制、文件体积和条目数限制作为基本文件处理约束，不新建治理模块。

### 13.3 启动和交付统一 V3

- 开发模式继续 Vite + 后端；常规桌面模式计划改为先构建前端静态产物，再由同一后端提供页面和 `/api/v3`，减少用户同时维护两个进程/端口。路由回退不能吞掉 API 404。
- 健康端点返回 build_id、schema_revision、API/能力版本、Worker 状态。启动器仅复用匹配当前构建且进程归属正确的服务；版本不同明确重启或提示。
- 安装依赖、构建、迁移和启动各阶段都能失败退出并指出日志；端口冲突、自定义端口、中文路径和空配置均有测试。
- 根 Docker/compose、CI、备份和 README 全部指向当前 V3。旧 V2 文档标历史，不能与当前手册并列声称可运行。
- 新人从干净代码库按一份短手册完成启动、模型设置、样例建模；不需要知道 Python/CMD/PowerShell 差异来排查正常路径。

### 13.4 性能预算与边界

以下是拟定验收目标，不是当前已经测出的性能；标准测试机暂定 4 核、16GB 内存、SSD，最终报告记录实际硬件与依赖版本。

标准规模：单项目 10,000 个对象、30,000 条关系、10,000 个材料片段、100,000 条系统记录/观测。大规模逐级增加，先记录曲线再决定是否迁移存储。

- 分页列表和常用局部图查询后端 p95 ≤ 500ms；本地初始工作台可交互目标 ≤ 2 秒，模型调用时间另计。
- 前端默认最多展示 300 个可见节点，展开/聚合受控；详情和邻居分页，不一次下载整个企业历史。
- 导入/导出分批处理，内存占用应随批大小而不是总行数线性增长；标准规模任务进度可见、可取消，吞吐基线在 T36 记录后锁定回归阈值。
- 上下文检索先用现有 SQL 筛选、文本索引与图邻域；语义向量可作为后续检索适配器，不作为可信事实来源或当前必要前置。
- 按 `(project, type, status)`、关系端点、源主键、指标/时期/维度、洞察身份/时间、队列状态/租约建索引；避免每轮分析读取所有历史后在 Python 聚合。
- 缓存包含明确基线/规则版本，变更后按受影响资源失效；全量重建只用于显式维护，不放在每次请求里。
- 本地模型调用默认单并发、任务预算明确。测到 CPU/存储瓶颈后才扩并发；本轮不引入分布式队列。

## 14. 测试、评估和“完成”的定义

### 14.1 固定合成企业验收集

至少三家公司、每家公司两个项目：制造企业（销售—排产—交付—回款）、服务企业（售前—项目—交付—收款）、贸易企业（采购—库存—销售—回款）。名称与数据全部合成，文档含访谈、问卷、职责、会议、绩效和经营结果。

每套包含正常情况及人工标注的：同名岗位、异码同物、同码异物、信息矛盾、未知职责、代理激励、合理取舍、难量化工作、日期错位、重复记录、缺失数据、否定反馈和有效反例。参考答案区分“可确定事实”与“管理者可接受的多种解释”，不要求开放管理问题只有一个标准答案。

### 14.2 验收分层

1. 单元与性质测试：类型、继承、生命周期、解析、身份、单位、时间窗、幂等、顺序无关性、反馈延续。
2. 服务/API 测试：事务、错误码、契约、批量预演、版本一致性、导入重算、发布与历史查询。
3. MOCK Agent：固定结构化输出验证工具循环、错误恢复、审批、临时引用、预算和上下文，不代表模型能力已验证。
4. 真实模型受控验收：使用合成材料，在用户批准模型调用与费用范围后执行；绑定实际输入、输出、工具轨迹和引用，不使用自报 action_keys/citation_count 计分。
5. 浏览器 E2E：从空实例开始，以真实后端完成上传/预览/确认、建模/编辑/发布、项目切换、查询/方案/反馈/导出，不用后台手填代替缺失界面。
6. 运行故障：双 Worker 领取、网络超时、中途取消、进程终止、旧库升级、备份恢复、重复点击与源 schema 漂移。
7. 性能与回归：固定规模、固定机器、留存原始结果，对比基线。

22 组探针全部转为正式断言并增加边界变体；不能保留“打印出错误结果却测试退出成功”的形式作为修复验收。

### 14.3 Agent 评估不是自报打分

评估区分：材料覆盖/引用真实存在、结构化字段正确、工具合法调用、批准前零正式写入、执行结果正确、任务完成率、管理分析的解释质量、反馈遵循、时间与成本。

确定性任务有明确断言；潜在关系用有说明的人工评价准则，记录争议和多解。任何模型评委只能作为辅助，不单独证明结论正确。引用存在与引用支持结论分别计，不以链接数量代替证据充分性。

### 14.4 发布门槛

- F01–F28 每项有实现/边界说明、对应测试和结果，不能仅改文案宣布完成。
- 无系统建模、有系统对齐、管理探索三条用户流程分别通过端到端验收。
- 不可执行格式/连接器/Action 不再表现成可用；失败可读、可定位、可恢复。
- 运行、迁移、导出恢复与 API 契约检查通过；不丢证据/反馈、不混版本、不以顺序覆盖来源。
- 有真实模型和真实只读数据库适配器测试记录，且明确尚未测试的厂商系统/文档特性。
- 不能证明绝对无 bug；最终交付附已测范围、剩余限制和复现材料，而不是笼统“全部完美”。

## 15. 开发顺序与阶段交付

详细依赖与逐项任务见[实施任务清单](D:/project/palantir/docs/30-v3-improvement-backlog.md)。顺序固定为：

1. **S0：冻结验收基线与契约。** 将反例转测试，记录现有数据和功能状态；不给未实现能力开可用标志。
2. **S1：先修明确的数据与状态错误。** 证据/反馈保留、PATCH、引用/类型、预演状态、旧 schema 升级保护、路由和缓存。
3. **S2：统一底层身份、指标和模型/数据快照。** 先定迁移与消费者，再落表；这是后续功能共同依赖。
4. **S3：材料处理与 Agent 执行闭环。** 解析器、材料上下文、工具注册、变更集、Worker 和回读。
5. **S4：无系统企业完整前端验收。** 交付第一条真正能用的产品链，不等待 ERP。
6. **S5：系统数据对齐纵向样板。** 稳定资产、映射、身份、观测、连接器、关系/事件/KPI 与语义导出。
7. **S6：管理探索、反馈、方案和案例。** 多对多证据、时间可比性、取舍重审、真实方案图、效果观察。
8. **S7：真实轨迹评测、项目恢复、交付和性能。** 统一 V3，完成故障、跨公司、换机与实际模型验收。

已形成的简单修复可以提前交付，但结构性变更不可跨过依赖强行并行。每阶段输出可运行版本、契约变更、测试记录、迁移说明和剩余限制；未过本阶段关键门槛不标完成。

## 16. 执行前已确定与仍需真实输入的事项

本计划已确定：单体 V3、三类 Agent、两种工作模式、共享本体身份、设计/现实分离、发布模型+数据快照、统一 KPI、批量变更、强约束直观链、开放探索潜在链、案例参考式积累。

不影响开始开发的外部待确认项：用户实际 ERP/MES 的连接方式和字段口径；真实模型调用的提供方/模型/费用范围；现有混合数据中无法从来源恢复的语义。这些先用合成数据验证标准能力，到实际接入/迁移决议时再请求具体输入，不靠猜测填满。

本轮只新增方案与任务文档，没有实施上述重构、修改业务数据库或派发开发任务。

## 17. 证明“对企业有用”，不只证明“代码能跑”

合成测试证明技术流程和已知约束，不能证明真实企业一定受益。在完整功能验收后，安排经用户授权的小范围企业试用，先选没有系统数据的企业，再选能提供只读系统数据的企业；不在本轮自行联系客户或导入真实资料。

试用前与管理层共同选定 10–20 个真正关心的问题，例如某流程为何需要这些岗位、谁有权处理例外、某考核是否鼓励局部最优、订单和回款为何在不同报表对不上。记录人工原流程的耗时、需要咨询的人、数据来源和已知答案，形成可比较基准。

分别验证：

- 建模价值：管理者能否从图和解释准确理解岗位/流程；模型遗漏和错误由人工纠正需要多大工作量。
- 数据价值：同一业务问题是否更容易找到正确口径，跨系统手工对表与重复分析时间是否减少；不能只看导入了多少行。
- 探索价值：建议是否提供了管理者原本未考虑的可用思路；误报、无关建议和已否定问题重复率是否可接受。
- 决策价值：方案的收益/牺牲是否明确，能否落到可执行变更；实际效果按约定窗口记录，同时保留副作用和外部因素。
- 使用价值：高管是否能独立完成查询和反馈，建设人员是否能独立维护，不依赖开发者每次在后台补数据。

每个试点开始前确定成功门槛和观察期，再做至少两轮反馈迭代；不事后只选择成功案例。若建模纠错成本超过节省时间、数据无法核对、管理建议长期低价值，应在对应环节改进后重测，不通过增加页面或 Agent 数量掩盖问题。减少分析岗位工作量是待验证收益，不是预先承诺裁减岗位。
