# 上游设计与下游运行投影

这是当前重构后的主流程约束：企业不因为有没有 ERP 而被分成两套产品。所有企业先建立同一种上游企业设计投影；具备系统数据的企业，再在同一项目中按需创建下游运行投影。管理层始终可以使用上游设计层，不能把没有运行数据误说成实际经营事实。

## 1. 两层分别解决什么问题

| 层 | 输入 | 产出 | 是否必需 |
|---|---|---|---|
| 上游：企业设计层 | 问卷、访谈、现场材料、制度文件 | 组织、岗位、能力、流程、信息流、资金流、岗位职责、流程衡量设计 | 所有企业必需 |
| 本体对齐层 | 上游设计概念和下游系统字段 | 稳定概念、设计绑定、字段映射、跨系统身份关系 | 上游建模与下游接入共用 |
| 下游：运行数据层 | ERP、CRM、MES、财务等系统或导出文件 | 对象、实体关系、事件、指标、血缘、实际流程表现 | 有系统数据时启用 |

下游不是上游的替代品，也不能直接覆盖上游。运行数据发现的“实际与设计不一致”，应成为修订建议，由人确认后生成新的设计基线。

## 2. 强制顺序

```text
创建公司 → 创建项目 → 导入调研材料
                    ↓
             企业设计投影
                    ↓
             发布设计基线 ─────────────→ 管理层设计查询
                    ↓（仅有系统数据时）
             创建运行数据投影
                    ↓
             本体对齐 → 数据预览 → 人工确认 → 运行对象/事件/指标
                    ↓
             设计—实际差异 → 诊断/因果/决策/行动/结果
```

设计基线是不可变快照，包含调研答案数量、设计节点、设计关系、岗位职责、流程衡量和代理风险等设计资源的清单哈希。每次重新发布都会产生新基线，旧基线不被覆盖。

运行投影必须保存 `design_baseline_id`。数据导入批次和统一导入预览也保存 `operational_projection_id`，因此任何运行事实都可以回答“来自哪个系统、哪次导入、属于哪个运行投影、对应哪个设计基线”。

## 3. 两类企业的出口

### 没有系统数据

完成调研、设计节点和关系、岗位/流程工作设计后，发布设计基线，再发布管理层版本。管理层可以查询“企业如何设计、岗位为何这样分工、流程目标是什么、哪些地方未知或难以量化”，回答必须标注为设计层证据。

### 有系统数据

先完成上面的全部步骤，然后创建一个或多个运行投影，例如“ERP 订单运行投影”“CRM 客户运行投影”。每次 CSV/API 接入都先预览，人工确认后才写入对象图；运行数据不会绕过本体层直接连接设计节点。

## 4. 代码契约

- `DesignBaselineRow`：上游不可变设计基线。
- `OperationalProjectionRow`：绑定某一设计基线的下游运行投影。
- `GET /projects/{project_id}/projection-context`：返回设计就绪度、当前设计基线和运行投影列表。
- `POST /projects/{project_id}/design-baselines/publish`：发布上游设计基线。
- `POST /projects/{project_id}/operational-projections`：创建下游运行投影；没有已发布设计基线时返回 `DESIGN_BASELINE_NOT_READY`。
- 正式开发者数据导入接口在没有运行投影时返回 `OPERATIONAL_PROJECTION_REQUIRED`。
- 旧的无前缀 `/api/v2` 只作为本地历史脚本兼容入口；正式开发者界面使用 `/api/v2/developer` 并执行上述门禁。

## 5. 为什么这样能持续扩展

新系统连接器只需要把数据落到运行投影，并复用已有的本体、映射、变更集和血缘接口；不需要重新设计问卷或企业设计层。新的行业模板也只提供可复用概念、关系和流程模式，不能未经目标企业证据确认直接写入其设计基线。
