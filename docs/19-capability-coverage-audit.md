# 重要功能覆盖审计

- 状态：已冻结
- 日期：2026-08-30
- 审计对象：`palantir` V2 当前代码与 13–18 号规划
- 目的：回答“现有方向能否实现所有重要功能”，并列出进入编码前必须补齐的设计契约

## 1. 审计结论

结论分为三层：

1. **产品闭环可实现。** 现有“管理层问题 → 调研 → 数字投影 → 数据验证 → 原因与情景 → 决策 → 行动 → Outcome → 学习 → 同行迁移”方向，能够实现本产品最重要的功能。
2. **当前代码尚未实现该闭环。** 当前 V2 是可运行的纵向骨架，已证明 Company、Project、Object、Link、Research CSV、Event、Metric、基础数据映射、Decision、Action、Outcome 和同步 AgentRun 可以落库并由页面操作，但大量能力仍是部分完成或未开始。
3. **18 号规划仍不足以直接编码。** 它定义了“做什么”和“大致顺序”，但没有完全冻结身份、版本、时间、纠错、并发、任务、包格式、错误、前端路由和迁移契约。若直接编码，各模块仍会临场设计并产生冲突。20、21 号文档补齐这些契约后，才进入执行式编码。

“所有重要功能”特指核心管理层企业解读产品，不包括替代 ERP/MES/CRM、自动经营企业、全行业实时数据平台、复杂权限产品、通用大数据平台和无人工监督的外部系统写回。

## 2. 审计方法

每项能力采用四级状态：

- `I`：已实现且已有实际测试；
- `P`：部分实现，有可运行骨架但不满足最终业务闭环；
- `N`：尚未实现；
- `D`：明确延后，不属于当前重要功能。

目标覆盖采用三种结论：

- `覆盖`：现有方向和后续精确规格可以完整承接；
- `补契约后覆盖`：方向正确，但进入编码前必须冻结契约；
- `不承诺`：主动排除，避免产品再次失焦。

## 5. 发现的设计缺口与处理决定

### 5.1 必须新增的八个横切基础

1. **稳定身份与不可变版本。** 资源 ID 代表身份，版本行代表某次内容；编辑、纠错、合并、退役均不能抹掉历史。
2. **业务有效时间与系统记录时间。** `valid_from/valid_to` 回答业务上何时成立，`recorded_at/superseded_at` 回答系统何时知道；二者不得混用。
3. **Projection 原子提交。** 调研确认、数据管道和 Outcome 回写必须先形成 ChangeSet，再一次提交 ProjectionVersion，禁止半批次写入。
4. **命令并发与幂等。** 所有副作用命令固定 revision 检查和 Idempotency-Key，避免重复点击、重试或两个页面互相覆盖。
5. **可恢复后台任务。** Pipeline、Agent、报告和项目包不得在 HTTP 请求中同步跑完。
6. **纠错优先于删除。** 语义资产、投影实例、结论和决策采用 supersede/merge/retire/archive；物理删除只允许未引用草稿和测试清理。
7. **统一错误与操作回执。** 前端不再猜测 FastAPI/Pydantic 错误结构；每个命令返回资源、revision、operation/job 和下一步。
8. **包与迁移版本。** 数据库 Schema、API、Ontology、Mapping、Projection、ProjectPackage 和 IndustryAssetPackage 各有独立版本，不用一个“version”字段混代。

### 5.2 现有代码与目标模型冲突

| 当前实现 | 问题 | 决定 |
|---|---|---|
| V2 使用 `metadata.create_all` | 无可重复升级、回滚和对账 | R1F 建立独立 V2 Alembic 链，运行时只迁移 |
| 类型和实例直接原地更新 | 不能 as-of、比较或可靠纠错 | R3–R4 拆稳定身份表与不可变版本表 |
| `project_id` 只由服务检查 | 某些跨项目外键组合无法由 DB 阻止 | 关键表增加复合唯一键和复合外键/触发校验 |
| LinkType 仅有端点 | 缺基数、方向、时间和逆向显示 | R3 扩展 LinkTypeVersion |
| Event 只挂一个 Object | 订单事件通常涉及多个参与者 | R4 增加 EventParticipant |
| MetricObservation 使用裸 `float` | 财务和口径精度不足 | 数值改 `Decimal/Numeric`，原始文本另存 |
| DataMappingProgram 只映射 Object | 无法连成业务图和时间线 | R6 统一声明式 Object/Link/Event/Metric Mapping |
| Lineage 只连 Object 与 SourceRecord | Finding、Decision、Outcome 不可追溯 | R6–R7 改通用 lineage node/edge 图 |
| CausalEdge 直接连 Object | 原因通常是变量而非对象 | R7 改连 CausalVariable，保留对象范围引用 |
| Agent 同步执行两个固定步骤 | 无工具、恢复、评测或真实协作 | R8 建立 Job 驱动的持久化运行时 |
| V1/V2 同时由应用挂载 | 最终用户路径和迁移边界不清 | R10 验收后停止 V1 挂载并删除冻结模块 |
| 默认数据库位于仓库 `./data` | 用户误提交真实数据的风险高 | R1F 默认迁移到本机应用数据目录 |

### 5.3 主动不实现的能力

以下内容不会伪装成“未来也许顺手实现”，而是明确排除当前路线：

- 替代 ERP/MES/CRM/OA/财务的事务录入；
- 自动写回外部核心系统；
- 无人工确认的企业事实生成；
- 无试点验证的“行业最佳实践”推荐；
- 通用数据湖、实时流平台、独立图数据库和微服务集群；
- 复杂多租户、RBAC/ABAC/DLP/加密交换产品线；
- 大企业全部部门、全部流程、全部系统一次性数字化；
- 在数据条件不足时声称 C2 以上因果结论。

## 6. 重要功能是否真正闭环的判定

只有最终浏览器旅程同时证明以下六个闭环，才能回答“已经实现所有重要功能”：

1. **认知闭环：** 管理问题 → 调研/现场证据 → 未知/冲突 → 已确认投影候选。
2. **数据闭环：** 多系统原始记录 → 映射/身份解析 → 同一对象关系图 → 完整血缘和重放。
3. **时间闭环：** Event/Metric → ProjectionVersion → as-of/差异 → 变化解释。
4. **决策闭环：** Finding/反证 → 假设/情景 → Option/Decision → Action/Outcome。
5. **学习闭环：** 人工纠正与 Outcome → Eval/LearningEvent → Pattern/Playbook 新版本。
6. **组织闭环：** 分部项目包 → 总部汇总/同行比较 → 行业资产包 → 目标企业 TransferTrial。

其中任何一个闭环若只能调用 API、手工改数据库、依赖未保存的内存状态，或重启后无法恢复，均判定为未实现。
