# 企业数字投影平台：精简内核、情景推演与 Action 完整重构方案

日期：2026-09-15。状态：实施基线；当前代码证据和明确边界见 [42 重构实施记录](42-refactor-implementation-status-2026-09-16.md)。

本方案综合公司中心化、极简管理系统、独立工作观察、情景推演和 Agent Action 的最新需求，替代 37、39、40 等文档中与其冲突的未来设计。旧文档和旧测试只作为实现背景，不能作为本方案的完成证明。

## 1. 产品目标与取舍依据

核心目标：让企业持续维护一份有来源的数字投影，让管理者查询现状、理解问题、尝试改变、比较后果，并把选定的调整提交给实际支持的执行流程。

保留五项价值：

1. 从问卷、访谈、制度和报告建立企业设计模型。
2. 按需接入信息系统，把对象身份和数据口径对齐。
3. 吸收日常观察，帮助管理者识别问题、设计取舍和潜在联系。
4. 在独立情景中执行假设动作，计算可计算部分，讨论其余影响。
5. 用独立工作采集工具补充岗位实际活动，提供简单对比。

第一性原理判断：功能必须服务信息取得、可信建模、语义统一、管理理解、行动推演之一。奥卡姆剃刀判断：同一身份、证据、状态推进、计算和执行规则只有一个权威实现；能复用就不增设第二套系统。

不以代码行数、表数、接口数、测试文件数作为验收指标。保留维护身份、类型、来源、修订、时间和执行一致性所需的结构。避免用大 JSON 容器和巨型服务掩盖复杂度。

## 2. 对此前方案的明确修正

| 此前建议 | 本方案决定 | 原因 |
| --- | --- | --- |
| 删除 Scenario | 保留隔离情景与差异能力，增加定量演算 | 是推演主链的必要基础 |
| Action 仅支持三个草稿/导出操作 | 保留通用执行内核，补齐查询、情景、计算、比较、内部变更 | Agent 必须可以完成实际工具操作 |
| 删除评测及其测试 | 从普通页面移走评测后台，保留自动化与真实模型业务评测 | 简化产品不应降低事实和计算质量 |
| 把全部数据塞进 10—12 张表 | 单数据库、明确领域表和类型，表数按约束需要决定 | 原始记录、假设和事实有不同生命周期 |
| 正式/观察/潜在/系统作为单一可信枚举 | 来源种类、证据状态、人工判断、业务状态分别建模 | 系统数据也会冲突；人工接受假设不等于证实 |
| 建设 Agent 合并全部上下文 | 一个建设 Agent 入口，建模和接入两种服务器控制的工具模式 | 共用企业知识，保持任务和写入职责分离 |
| 一个主项目代表统一企业 | 正式资源直接归属 company_id；取消项目所有权层 | 旧数据不要求迁入，本轮无需长期保留默认项目 |
| 删除学习能力 | 保留用户指定历史案例的参考，移除独立飞轮平台 | 复用经验有价值，问卷和现实证据仍是建模依据 |

## 3. 当前基础与缺口

此次检查确认的可复用基础：

- portfolio.py 有公司到主项目指针，但 create_project 仍能创建独立容器。
- projection.py、ontology.py、changes.py 有类型、对象、关系、变更及修订检查。
- publication.py、query_snapshots.py 有发布图与查询基线实现。
- collaboration.py 的 Scenario 可表达结构覆盖、比较变更及应用；尚不是指标连锁演算引擎。
- tool_registry.py、actions.py 有工具契约、预演、执行、幂等和运行记录；核心存在 ERPNext 专用逻辑。
- task_classifier.py 区分语言理解候选；task_routing.py 提供程序路由校验。
- 管理 Agent 页面已经允许未发布公司保存观察，但与旧管理表单和领域数据并行存在。
- agent_runtime.py 在无模型配置时仍回退到 MOCK 标记的本地规则，需要拆分真实智能能力与确定性离线能力。
- 建模页的发布入口仍跳到系统接入页面，图编辑也是另一页面；导航精简尚未完成流程收敛。
- 工作采集器已有独立缓存和上传路径；其配置仍使用 project_id，浏览器扩展在现有说明中是额外部署项，不能当作已交付。

本地旧数据清理之后，目标采取干净初始化。实施前重新检查是否出现新录入的数据、运行任务或有效导出；不假定所有目录始终为空，不自动删除桌面原报告或其他项目文件。

## 4. 用户界面与使用顺序

### 4.1 建设端：三个入口

**企业**：创建、选择、修改和归档公司；显示材料覆盖、模型版本和接入状态。新公司无需创建项目。模型设置和备份入口放全局设置。

**材料与企业建模**：同页提供材料清单、预览导入、建设 Agent、草稿差异、图与详情编辑、审核发布。按阶段打开对应区域，避免全部表单同时铺开。

**信息系统接入**：提供来源登记、样本与快照、映射建议、身份对齐、冲突处理、查询与导出。复用现有企业对象，接入属于可选下游流程。

### 4.2 使用端：两个入口

**企业数字投影**：组织岗位、职责权限、流程流动、系统对应四种业务视图；岗位详情显示工作观察。每种视图使用同一对象目录，不建立第二套投影。

**管理 Agent**：一个对话入口，内部提供“查询与分析”和“情景推演”两种模式。观察输入、候选确认、来源、保存的情景和方案比较作为消息卡片或抽屉。

对话支持新建、重命名、删除；删除对话不会删除独立材料、已经接受的模型、观察、情景或动作记录。删除动作本身留痕；界面说明独立保存的内容范围。

工作观察导入和统计放在投影内的岗位观察区域；管理人员可统一选择公司范围和时段，再下钻员工/岗位。无需增加主导航。

### 4.3 无系统与有系统的企业

所有企业先有公司对象和资料，逐步建立部门、岗位、职责、权限和流程。没有 ERP 的企业可完成建模、管理观察和定性推演。数量、产能等可以由人补充，但必须标明是已核实输入还是情景假设。

有系统的企业继续接入，形成正式对象上的已验证运行数据；接入新批次不要求重建组织模型。管理观察在发布前即可输入，正式查询按实际可用模型和数据决定能否运行。

## 5. 技术架构

保留 React、现有图组件、FastAPI、Pydantic、SQLAlchemy 的技术栈；使用模块化单体和一个平台数据库，避免在此次领域重构中额外替换框架。

后端划分为八个领域模块，每个模块按需要有自己的模型、服务和接口：

| 模块 | 权威职责 |
| --- | --- |
| enterprise | 公司、类型、对象、关系、结构版本、变更发布 |
| evidence | 原始材料、证据定位、管理观察、潜在认识 |
| integration | 连接器、原始批次、身份、映射、冲突、统一数据 |
| query | 查询基线、对象读取、指标定义与确定性查询 |
| scenario | 情景定义、动作序列、演算、敏感性及方案比较 |
| agents | 对话、模型适配、上下文、任务理解和工具循环 |
| actions | 工具注册、执行校验、任务队列、确认与结果记录 |
| work_observation | 设备归属、事件摄入、片段、路径和岗位比较 |

公共基础设施只处理配置、数据库事务、标准错误、审计和文件存储。模块之间经领域服务调用，不复制业务正文作为另一份权威记录。

员工端另有 collector 和 browser-extension 两个独立发布物。它们不依赖管理平台前端包，也不运行管理 Agent。

## 6. 数据架构与公司统一身份

### 6.1 一个物理数据库、明确的逻辑边界

平台默认一个 SQLite 数据库，附件位于同一实例的数据目录；采集器仍有自己本地的待上传缓存。正式、观察、潜在和控制在平台库内用独立表、类型和服务写入边界区分。

| 逻辑领域 | 主要资源 | 使用规则 |
| --- | --- | --- |
| 企业模型 | company、object_type、entity、relation、relation_participant、model_release | 正式结构按审核后的版本读取 |
| 证据与认识 | source、evidence_fragment、observation、potential_record | 保留原文、时间、支持/反证与人的判断 |
| 系统运行 | source_system、raw_batch、raw_record、identity_binding、mapping、assertion、conflict、dataset | 校验后才参与正式数据查询 |
| 查询与推演 | metric_definition、query_baseline、scenario、scenario_revision、scenario_run | 运行输入与结果可复现 |
| Agent 与执行 | conversation、message、task、action_invocation、confirmation、audit_event | 保存执行事实和资源引用 |
| 工作观察 | device_binding、work_event、analysis、comparison | 事件为原始观察，片段与路径为可重建结果 |

以上为资源职责；实施时可合并同生命周期且具有相同约束的物理表，不强制每个名词新建表。不把不同生命周期资源压成同一个无约束 JSON。

### 6.2 范围和身份

- 企业资源直接引用 company_id，关系参与者、映射目标、证据引用都验证同公司。
- 不再创建 EnterpriseSpace 和默认 Project 双重所有权层。
- 公司登记是公司身份的唯一权威来源，图中的公司根节点从公司记录映射生成。
- 部门、岗位、人员、流程、职责分别建模；同名不等于同一对象。
- 一个员工可以兼任多个岗位，任职记录有业务生效区间。
- 来源身份使用“公司＋系统＋源对象类型＋稳定主键”定位；名称相似只生成候选。
- 方案、视图、对话和材料批次均不是新的公司或投影。

### 6.3 四类状态分别保存

1. 来源类别：材料、系统记录、管理者输入、工作事件。
2. 证据状态：未核实、支持、冲突、反驳、失效。
3. 人工判断：待决定、接受、拒绝、撤回。
4. 业务性质：现状、制度要求、目标设计、建议、情景假设。

潜在认识的人为接受表示值得保存；它仍是可被推翻的假设。情景运行输出始终标记为推演结果，不能仅通过改变状态变成现实事实。

所有人工新增、修改、确认、拒绝、撤回、归档和删除记入 audit_event，包含操作者、时间、理由（需要时）、前后修订、对象及任务引用。单机身份显示为本机操作者，不虚称已识别现实中的具体人员。

### 6.4 时间和版本

业务发生/生效时间与系统记录时间分别保存。默认查询为“该基准建立时已知的指定期间数据”；回溯修正显式建立另一基准。

QueryBaseline 固定：company_id、模型版本、映射版本、原始批次/物化版本、截止时间、纳入的观察及潜在认识修订、工作观察分析版本和过滤范围。图、查询、推演、导出共同引用该基准。草稿分析使用明确的 draft_revision，不能显示为已发布状态。

## 7. 企业建模与图形

建模流程：资料预览 → 确认导入 → Agent 提取 → 草稿差异 → 图形修改 → 校验与接受 → 发布。

材料支持 DOCX、TXT/Markdown、PDF 文本、CSV、XLSX、JSON。扫描 PDF 无可读文本时明确提示提取限制；自动 OCR 不作为初版必需。外部问卷系统通过通用导入格式或独立格式适配器接入，核心不内置问卷平台。

提取项必须关联原文定位和来源版本，区分现状、否定、制度、建议与未知。例如“没有研发部门”不创建研发部门，“建议设预算流程”只形成建议。引用检查只能证明引用存在和归属合法，不能替代语义支持审核。

岗位模型保留：职责、目的、权限、输入输出、所需能力、知识依赖、协作关系、战略关联、指标及难量化部分。绩效指标同时标注口径、可控性和可能的局部目标冲突，供管理 Agent 探索代理问题与组织取舍。

正式图的节点与关系支持增、查、改、退役；人工和 Agent 修改使用同一变更服务。发布时分别显示结构校验、证据覆盖、未核实内容、人工接受结果。结构错误或悬空引用阻断，未知业务信息保留为缺口。

图提供四种过滤视图：组织岗位、职责权限、业务流程/流动、系统对应。普通二元关系直接画带标签的边；多参与者关系按需展开。选中对象可查看原文、实际数据、差异和历史；正式关系、观察关系、潜在假设、情景变化使用不同样式和图例。

## 8. 通用系统接入

初版优先交付文件导入与通用 REST JSON 只读连接器。现有 SQLite/PostgreSQL 只读能力若测试通过可作为可选适配器保留，不要求普通用户理解数据库。ERPNext 作为扩展测试样例，核心不以它为前置。

连接器统一声明结构检查、样本读取、分页/增量、稳定键、时间、删除语义和只读能力。系统接入流程为：来源 → 样本 → 原始快照 → 映射 → 身份 → 关系 → 冲突校验 → 物化 → 数据集查询/导出。

映射按对象、属性、关系、身份、单位、状态、时间、金额口径显式定义。首次采用或歧义映射需人工确认；已经确认的精确规则可以对后续批次自动执行。没有主键、单位或状态含义时保留缺口。

原始层不可变；撤销和更新生成新版本。不因某次增量文件缺少一行就推断该对象被删除。更改映射后产生新物化版本并保留旧来源引用，不原地覆盖已有查询基准。

统一数据集保留字段类型、行粒度、连接键、基数、多值处理、单位和时间定义。遇到一对多连接导致金额重复时阻断或要求明确聚合口径。

导出包含模型/本体、数据集、来源索引、冲突、工作观察和推演结果，按资源提供 CSV/XLSX/JSON 或打包格式；附模型、映射、数据时间、过滤范围、覆盖与缺失说明。

## 9. Agent 架构与任务路由

### 9.1 两个用户级 Agent，共用运行引擎

**建设 Agent**有建模模式和接入模式。模式切换保留企业公共知识，以任务摘要衔接；各模式独立消息上下文、检索范围和工具集合。建模模式写模型草稿，接入模式写映射草稿并执行已经允许的只读同步。Agent 不自行批准正式变更。

**管理 Agent**将观察输入、查询、探索、推演和方案选择作为内部任务阶段。可以读当前公司相关的正式数据、证据、观察、潜在认识、工作观察和历史情景；服务按任务及基准约束读取。

自然语言由模型解释，目标解析、单位时间、数据可用性、工具权限和最终执行由程序核验。不得把关键词路由描述成可准确理解任意管理意图。

### 9.2 任务类别

| 类型 | 执行方式 | 返回方式 |
| --- | --- | --- |
| 输入观察 | 保存原文，关联对象，生成可修改摘要 | 明确已保存及归属，不提升为事实 |
| 简单查询 | 已注册查询，目标/口径完整，正式数据可用 | 简单任务标识、结果、必要口径 |
| 复杂分析 | 相关数据检索、图扩展、对照与替代解释 | 来源、事实/观察/假设、冲突、缺口、取舍 |
| 情景推演 | 形成条件与 Action，执行独立情景并计算 | 影响图、数值差异、条件与未计算部分 |
| 明确动作请求 | 校验真实能力、范围和确认条件后执行 | 实际完成的操作及回执 |

推演含潜在机制时按复杂任务读取规则处理；单纯按既定公式重新计算可直接使用确定性工具。简单查询缺数据就返回缺口，不能悄悄变成猜测数字。

### 9.3 上下文与模型

所有 Agent 共用企业目录和 QueryBaseline；对话历史用于理解任务，不作为企业权威事实。按需检索并记录实际读取清单、引用清单和未覆盖范围，避免全库重复塞入上下文。

无模型配置时保留手动建模、确定性查询、已定义计算和导出；智能提取与探索明确提示需配置模型。规则模拟器仅用于显式测试。正常运行记录实际模型、工具及版本，不伪造已理解全部材料。

同岗位或同类企业的历史经验通过用户指定案例检索；输出说明适用条件与差异。参考内容不能作为目标企业的现实证据。保留人工经验与实际结果反馈，不新建训练、排行榜、自动发布或行业飞轮平台。

### 9.4 潜在问题的双向分析

潜在分析同时支持两条路径：从战略、组织、职责、权限、激励和考核的设计出发，寻找局部目标冲突、难量化责任、能力依赖和不可避免的取舍；从会议、汇报、实际绩效、企业成果和工作观察出发，寻找实际偏差及替代解释。两条路径指向同一问题时突出显示“设计与观察同时支持的候选”；只有一条时显示“单侧线索”。这只是提醒方式，不是自动证实或因果判定。

Agent 可以在相关企业信息基础上从第一性原理提出组织重设计与多个方案，不限制为固定的检查清单。分析视角、提示模板、证据检索策略和结果结构均可独立扩展；客观对象解析、引用和数据计算仍使用公共工具。用户明确确认才保存潜在认识，并保留支持、反证、适用条件和后续实际结果；不设置自动升级为正式事实的分数阈值。

## 10. 情景推演模块

### 10.1 基本定义

一次推演是“基准＋外部事件＋可选行动＋假设与演算规则＋运行结果”。外部事件可以是停供、需求变化、离职、政策变化；可选行动可以是替代采购、增加资源、调整职责或流程。

支持比较基准、不采取应对和用户选择的一个或多个方案；不强制每次创建多个方案。非比较变量保持一致；“最佳”必须依据管理者选择的目标和约束，不能自行虚构综合分数或全局最优结论。

### 10.2 三种结果

| 结果 | 依据 | 表达 |
| --- | --- | --- |
| 结构影响 | 企业依赖图和明确关系 | 受影响对象及可能传播路径，不宣称影响已发生 |
| 条件计算 | 公式、业务约束、明确参数 | 基准、推演值、差值、单位、期间、规则和假设 |
| 探索性推测 | 材料、观察、潜在机制及管理知识 | 替代解释、可能后果、待验证条件 |

组织关系、时间相邻或数据相关均不自动构成因果关系。把事件或行动转为数量影响，需要显式影响规则；缺少规则时只能查找结构影响或提出机制假设。

### 10.3 初版演算能力

支持有类型的数值输入、聚合、比例、条件表达式、容量上限、库存收支、订单积压、资源分配和明确公式的成本计算。每个规则有版本、输入、输出、单位、周期、适用条件及测试案例。

通过白名单表达式树和注册函数执行，禁止 eval、模型生成脚本及任意 SQL。Agent 可建议新公式，由规则编辑器生成结构化定义、经校验后在情景中试用；经业务核实时才成为正式指标规则。

按依赖顺序计算。跨日状态使用显式前一时段引用；同一时段循环依赖初版返回未支持，不以多次随意迭代伪装求解。检查重复计入、单位冲突、分母为零、超范围参数、时间错位和双重资源使用。

敏感性初版做有界参数组合或上下界计算，保存所有条件；情景范围不是统计置信区间。预算限制运行数量和时间，展示计算范围和未运行条件。

### 10.4 具体验收算例

需求 90 件/日、产能 100 件/日，降至 80 件/日持续 5 日，初始库存和积压为 0，无加班、外包或流失：基准完成 450、积压 0；受影响情景完成 400、期末积压 50。加班方案仅在显式增加产能并给出成本条件时重算。利润、流失概率、压力等未定义指标必须保持未计算。

该算例是有明确前提的演算验收，不代表现实企业的通用生产规律。

### 10.5 结果与修订

情景可新建、复制、修改、比较、归档和删除（留痕）；每次运行冻结输入、规则版本和结果。修改条件只失效依赖的结果；不能确定影响范围时全量重算。新数据不会悄悄改写旧推演。

界面显示假设卡、影响图、指标差异、方案取舍、来源和未计算部分。用户决定采用后，生成正式模型变更草稿；尚未实施的目标设计仍标记为目标，不能因批准而成为现实运行状态。后续实际结果作为独立观察反馈。

## 11. Action 内核

### 11.1 通用契约

ActionSpec 作为唯一注册定义，包含 key/version、输入输出类型、允许的 Agent 模式、执行目标、前置条件、影响范围、确认要求、执行器、结果核验、幂等策略及可用能力。由它生成模型工具契约、接口类型和前端动作卡片。

执行目标分别为 READ_ONLY、SCENARIO、PLATFORM、EXTERNAL。用户请求、公司范围、基准、模式和允许动作由服务端注入；模型不能修改目标环境或伪造批准记录。

内部平台动作包括保存观察、提案、确认后的潜在认识、应用已经接受的模型变更和导出。管理 Agent 提交模型草稿；正式应用交给建设流程的变更服务。

### 11.2 工具能力

| 组 | 核心工具职责 |
| --- | --- |
| 企业与来源 | enterprise.query、evidence.read、observation.search、potential.search |
| 建模与接入 | projection.propose/validate、source.inspect/import、mapping.propose/validate、dataset.query/export |
| 情景 | scenario.create/modify/validate/run/compare/sensitivity |
| 内部写入 | observation.save、potential.propose/confirm、proposal.create/accept/apply |
| 工作观察 | work_observation.read/compare |
| 结果 | result.export |

工具名称为目标契约。confirm/accept/apply 仅在匹配服务端已有人工决定与版本时可调用，不向模型开放“生成批准”的权力。普通读取和情景内操作可在任务预算内连续执行。

### 11.3 执行生命周期

执行状态：QUEUED、RUNNING、SUCCEEDED、FAILED、CANCELLED、UNKNOWN。校验状态、是否等待人确认以及业务任务结果分别保存，避免将多种状态笛卡尔积成巨大状态机。

业务结果：ANSWERED、PARTIAL、NEEDS_INPUT、UNSUPPORTED。工具成功不自动令业务问题已解决。

确认绑定内容摘要、对象范围、动作版本和基准修订。参数或目标变化后重新形成确认内容。多个动作可作为一个明确范围的变更集批量确认，不逐个字段弹窗。

同一公司、动作和幂等键的重复请求返回原结果；相同标识但内容不同返回 409。Action 定义无需每家公司复制一份，实例只保存引用和公司的配置差异。

使用一个轻量持久任务队列和 worker 支持模型请求、导入、演算与导出。短事务更新状态，长模型/网络请求不持有数据库写锁。重启恢复已排队任务；重试遵守动作的幂等和结果核验约定，不能声称任意外部副作用 exactly-once。

### 11.4 同一业务动作的情景与真实执行

例如“增加采购量”有共同的业务输入，但可以分别注册情景执行器与未来采购连接器。情景执行器增加计划到货/支出并触发演算；真实执行器创建外部采购请求。二者单独声明支持情况，不能把情景执行成功解释为真实采购完成。

下采购单、订单接受、发货和入库是不同事件；库存变化需要指定到货条件或真实回执。

当前交付情景和平台内部执行。外部扩展提供 Protocol/接口、能力清单、预览/执行/回查契约和测试假实现；生产默认不注册外部写入。已有 ERPNext 逻辑移出核心，只有扩展安装且真实验收通过时才显示支持。结果未知的外部操作先回查，不能直接重复执行。

## 12. 独立工作观察

员工端独立 Windows 采集器采集时间、设备、会话、应用类别、前台活动、空闲/暂停/锁屏状态和事件顺序。浏览器页面类别通过独立扩展提供；只使用必要业务域名/类别，不从桌面窗口标题推断具体网页。

采集范围和运行状态对员工可见，支持暂停；不采集键盘内容、鼠标具体点击、密码、持续截图、录像或全部浏览历史。窗口变化用于识别活动切换，不默认上传原始窗口标题或完整 URL。业务分类采用版本化允许规则，未知类别保留未知。

平台管理员配置设备到公司和员工的关联。员工无须安装或登录管理平台。扩展通过明确版本的本地消息接口或本地桥接进入采集缓存，不能直接访问平台数据库。桥接不可用时标记页面类别未知。

在线批量上传和离线包使用同一事件标识、内容摘要和去重流程。只有服务端明确确认持久接收的事件才从缓存清理；离线导出不代表接收成功。乱序补传按业务时间排序；重复内容不重复计数，冲突内容拒绝覆盖。

绑定保存 valid_from/valid_to 和 recorded_at，拒绝同范围歧义重叠；历史事件按发生时间解析身份和岗位。多设备重叠标注而不是双倍计算工作时长。

统计只包括连续活动片段、相邻转换、连续 2—4 步路径、工具使用时长、覆盖/缺口及同岗位差异。空闲、暂停、锁屏和采集缺口切断路径；不同员工、设备或会话不拼接路径。

前端标记“观察到的活动顺序”，不视为完整任务、因果链、绩效分数或最佳 SOP。与绩效比较时另行指定真实结果及匹配口径；可推广与否由管理者判断。

## 13. 接口与前后端公共契约

保持 /api/v3；资源按公司组织，取消前端 project 参数与选择状态。主要接口族：

- /companies
- /companies/{company_id}/projection、types、entities、relations、releases
- /companies/{company_id}/materials/imports、sources、evidence
- /companies/{company_id}/source-systems、mappings、identities、conflicts、datasets
- /companies/{company_id}/observations、potential-records
- /companies/{company_id}/baselines、metrics、scenarios、scenario-runs
- /companies/{company_id}/conversations、tasks、actions、exports
- /companies/{company_id}/work-observation
- /ingestion/work-observation/batches

实际端点按资源和操作定义，不强压成 25 个万能接口。读、预览、校验与写入含义分明；GET 不创建隐式资源。

公共约定：预览有编号、内容摘要、基准修订和有效期；确认必须匹配。长操作 202＋operation_id，统一任务查询/事件流；409 为内容/版本冲突，422 为参数不合法；无能力、失败、部分结果和未知明确返回。所有列表支持有限分页。

OpenAPI 从实际路由生成，再生成前端类型；CI 检查漂移。前端不手写另一份业务契约，Mock 复用同样的结构与校验并明确显示测试环境。

## 15. 启动、数据切换与文档

提供 setup（安装依赖）、build（类型/契约检查和构建）、launch（启动已构建版本）、stop（停止当前实例）、reset（明确范围清空）五类职责。日常 launch 不执行依赖安装或前端重建；缺构建产物时给出明确的一键初始化入口。

统一配置解析：CLI、桌面启动器和开发服务遵循同一数据目录规则。显示实例 ID、版本和数据目录；开发验收使用独立端口/目录。局域网采集需可配置绑定地址和上传地址，默认本机模式与内网模式明确，不能只改客户端 URL 而服务仍仅监听回环地址。

平台空白初始化采用新单库结构。当前旧实例如有新增业务数据，切换前导出/保留并报告，不自动清空。旧项目接口与旧包不作长期兼容；识别到旧格式时返回清晰错误或明确的离线转换路径，不静默导入为新事实。

新结构从干净的迁移基线开始；保留正常的后续 schema 迁移机制。代码、脚本、测试夹具和文档进入仓库；数据库、原报告、采集包、密钥和模型响应不进入仓库。

运行备份仍要存在：单库使用一致性备份，附件附清单及摘要；恢复验证库和附件引用。测试原始数据留存策略明确，采集原始事件未过保留期不能为了压缩表数删除。

最终活动文档按职责收敛到 README、ARCHITECTURE、USER_GUIDE、EXTENSIONS（含连接器、Action、演算规则与采集协议）；旧文件归档并标记适用版本。本方案在交付后转为实施记录，完成状态以逐项证据更新。

## 17. 验收与质量标准

### 17.1 三家合成企业

- 服务企业：无信息系统，报告含现状、否定、建议、同名岗位及相互矛盾陈述。
- 制造企业：ERP 订单、MES 产能和 CRM 客户异名数据，含单位、时间、身份和一对多聚合冲突。
- 共享服务企业：多部门、员工兼岗、人员调动、多设备及多个情景，验证同公司积累与跨公司隔离。

### 17.2 必过测试

1. 创建公司后立即可导入材料；多次导入和多次对话维护同一对象目录。
2. DOCX/表格等在浏览器预览并确认，重复导入、解析失败有明确结果。
3. 否定、建议不进入现状；关键对象和关系能打开支持它的原文。真实模型输出有人工预期清单核对。
4. 节点/边增改退役、草稿差异、过时修订冲突、版本切换和发布均可操作。
5. 无模型时不伪装智能建模成功；人工编辑、确定性查询和计算仍可用。
6. 三类系统样例能预览、映射、身份对齐、冲突处理和导出；同名异物、未声明单位不自动合并。
7. 查询、图、导出使用同基准；新数据不重写旧结果；关系连接不重复计数。
8. 管理输入只有一个原始权威记录；假设经人接受仍不成为正式事实。
9. 简单任务缺口明确；复杂任务实际引用、冲突及未读取范围可查。
10. 情景动作改变假设状态并产生可验证结果，不改变正式模型和外部系统。
11. 产能算例、库存状态转移、敏感性上下界准确；循环、缺值、单位冲突明确失败或部分完成。
12. 同基准方案可比；修改假设生成新运行；旧结果仍可重现；缺少因果机制时不输出伪精确影响。
13. Action 幂等、范围、参数、确认摘要、失败、取消、重试和恢复正确；未安装执行器返回未支持。
14. 采集器在无管理系统的员工端运行；扩展页面识别实际验证，缺失时显示未知。
15. 在线与离线重复导入不重计；断网、锁屏、暂停、乱序、调岗回溯和多设备重叠处理正确。
16. 工作路径不跨员工/会话/缺口拼接；比较不自动给出绩效排名或最佳流程。
17. 所有人为操作与删除有留痕；对话删除与独立企业资源的生命周期一致。
18. 一键启动读取同一实例；备份恢复完整；测试不占用正式端口或混入真实资料。

浏览器完整主链：建公司 → 导材料 → Agent 草稿 → 图形纠错 → 发布 → 接入系统样例 → 对齐及导出 → 保存管理观察 → 查询 → 设定事件 → Agent 执行情景动作 → 比较与修改参数 → 导出推演依据 → 提交选定模型草稿 → 导入工作观察 → 岗位对比。

测试分为纯规则、服务/事务、接口契约、浏览器、真实模型、独立采集。按功能风险保留测试，不减少到固定文件数量。既有全部测试通过也不替代新主链验收；一次真实模型成功不意味着所有企业和任意问题均已正确。

## 18. 本轮交付与延后边界

本轮交付五项核心价值、两个 Agent 入口、两种建设工具模式、情景计算与平台内 Action，以及连接器/计算/外部 Action 的明确扩展位置。

延后：生产 ERP/MES 写入、行业调度与优化算法、员工推广培训/消息分发、绩效评分、自动最佳流程判断、因果发现/识别引擎、模型训练、向量基础设施、微服务、多租户管理平台和云高可用。基础公司范围、凭据保护、类型检查和审计仍属于现有功能正确运行的一部分。

最终验收判断：企业可以维护一份可核查投影，管理者能问清楚现状、提出假设、让 Agent 真正执行内部工具和演算、比较后果并提交选定调整；每项结果都能解释来自何处、采用哪些条件和实际执行到哪一步。
