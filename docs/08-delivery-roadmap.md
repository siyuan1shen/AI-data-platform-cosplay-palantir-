# 交付路线与验收（历史版本）

> 本路线已停用，不再以安全治理、交换协议或生产基础设施为当前交付重点。现行资源分配、阶段和验收门槛见[集中交付路线图](16-delivery-roadmap.md)。

## 1. 交付原则

项目以可验收的纵向闭环推进，不以页面数量、Agent 数量或微服务数量衡量进度。每个阶段都必须包含契约、迁移、权限、审计、测试和运行手册。

首个业务纵切选择制造企业的“客户 → 订单 → 交付 → 开票 → 回款”，因为它能同时验证问卷、跨系统同义映射、实体解析、冲突处理、Agent 分析和企业解读。

## 2. 阶段总览

| 阶段 | 主要结果 | 退出条件 |
|---|---|---|
| 0. 工程与契约基线 | 独立仓库、领域契约、ADR、CI | 核心模型和状态机测试通过 |
| 1. 可信内核 | 租户、证据、Artifact、审核、审计 | 任一正式结论可追溯且不可静默覆盖 |
| 2. 调研工作台 | 问卷、访谈、附件、追问 | 一家公司可完成端到端调研 |
| 3. 语义集成 | Source Catalog、映射、实体、冲突 | 三个系统的关键对象可统一解读 |
| 4. 多 Agent 诊断 | 受控 DAG、模型网关、专业 Agent | 固定评测上稳定产生可审核提案 |
| 5. 企业解读产品 | 企业全景、价值流、风险、证据视图 | 非项目开发者可验证主要结论 |
| 6. 扩展平台 | SDK、Program、Recipe、Playbook Registry | 新行业模块不修改核心即可安装 |
| 7. 行业共享飞轮 | 贡献、脱敏、评测、签名、发布 | 共享资产带来可测 Flywheel Lift |
| 8. 整改与规模化 | Action、复查、企业安全、容量 | 诊断到业务结果形成闭环 |

工期由团队规模和真实数据质量决定。每个阶段先过退出门槛再扩大范围，不以日期强行掩盖未解决的语义与安全问题。

## 3. 阶段 0：工程与契约基线

### 交付物

- 独立 Git 仓库和 `src` 工程结构；
- 配置、日志、健康检查和测试框架；
- Artifact、Agent、Event、Extension 公共契约；
- 工作流状态机和非法转换保护；
- 架构总纲、ADR、API 和安全基线；
- lint、类型检查、单元测试命令。

### 验收

- 外部问卷系统无任何改动；
- 公共模型拒绝未知字段并默认不可变；
- 终态运行不能重新进入执行态；
- `/health` 和 `/ready` 有稳定结构；
- 仓库不包含密钥、密码、企业问卷和回答；
- 从空环境可按 README 启动。

## 4. 阶段 1：可信内核

### 交付物

- Tenant、Workspace、Membership 和 Policy Context；
- Source、Evidence、Artifact、Review、Conflict、AuditEvent；
- PostgreSQL/SQLite Repository 与 Alembic；
- 事务 Outbox、幂等命令和乐观并发；
- 本地对象存储抽象；
- 凭据保险箱接口和 BYOK 管理；
- 审核队列和证据链 API。

### 验收场景

1. 导入一段问卷回答后生成内容摘要和 Evidence；
2. Agent 提案不能直接成为 Finding；
3. Reviewer 批准后形成新 Artifact 版本；
4. 两个冲突事实同时保留并进入冲突中心；
5. 跨租户 ID 探测返回不可区分的拒绝；
6. 删除 Evidence 后派生索引进入清理队列；
7. 每一步均可通过审计事件重建决策链。

## 5. 阶段 2：调研工作台

### 交付物

- QuestionPack、Question、Condition 和版本发布；
- Company Assessment、Department、Respondent 和邀请；
- 文本、数值、枚举、表格和附件回答；
- 草稿、提交、冻结和补充回答状态；
- 追问 Agent、遗漏检测和访谈记录；
- 问题与答案合并导出，过滤无回答项；
- 调研覆盖率、证据充分度和待追问看板。

### 验收

- 同公司、同问卷、同问题的多份有效回答能保留来源并生成合并视图；
- 无回答内容不进入默认导出；
- 问卷版本升级不改变历史 Assessment；
- 追问建议绑定原问题、回答和理由；
- 企业私有问题不会误进入共享 QuestionPack。

## 6. 阶段 3：语义集成

### 首个纵切

接入 CRM/ERP/财务三个样例源，统一：

- 客户；
- 销售订单；
- 交付单；
- 发票；
- 收款；
- 金额、币种、时间和状态口径。

### 交付物

- Connector SDK、Source Catalog、Schema Snapshot 和 Profiler；
- 字段、枚举、单位、时间和公式映射；
- Canonical Entity、External Identifier、Alias；
- 确定性规则 + 候选评分 + 人工确认的实体解析；
- 数据血缘、权威来源策略、冲突中心和 Schema Drift；
- Mapping Program 测试和回放环境。

### 验收

- 同一客户在三个系统的别名可正确链接且可撤销；
- 同名不同客户不会被自动合并；
- 单位和币种转换保存原值、公式和版本；
- 订单金额口径冲突不会被平均或覆盖；
- 任一统一指标可追溯到源字段与转换程序；
- Schema 漂移会阻断不安全映射并告警。

## 7. 阶段 4：受控多 Agent 诊断

### 首批 Agent

- Research Agent：整理证据与缺口；
- Follow-up Agent：生成追问提案；
- Schema Agent：提出字段和枚举映射；
- Ontology Agent：提出概念、关系和别名候选；
- Diagnosis Agent：提出问题、根因和影响；
- Summary Agent：生成管理层摘要；
- Critic Agent：检查证据、矛盾、过度推断和格式；
- Privacy Agent：检查共享与导出风险。

### 交付物

- Agent Catalog、任务契约、确定性 DAG 编排器；
- Artifact Blackboard 和版本快照；
- Model Gateway、预算、超时、重试和缓存；
- 人工门禁、暂停恢复和失败补偿；
- Prompt/Recipe Registry；
- 固定 Eval Suite、回放和模型/知识分离评测。

### 验收

- 同一输入和版本快照可重放；
- Agent 无法读取未授权 Workspace；
- 达到预算后工作流明确终止；
- Critic 不能直接覆盖上游结果，只能提交审查 Artifact；
- 无证据高风险 Finding 被阻止发布；
- 更换模型和更换知识版本可以分别测量影响。

## 8. 阶段 5：企业解读产品

### 交付物

- 企业概览与组织/系统地图；
- 从客户到回款的价值流；
- 实体 360、指标口径和数据血缘；
- 风险、根因、证据与冲突工作台；
- 自然语言查询的引用式回答；
- 报告构建器、版本对比和导出；
- 面向管理层、顾问和 Data Steward 的不同视图。

### 验收

- 新用户可在 30 分钟内定位主要系统、流程和风险；
- 每个图表数字能下钻到 Fact/Evidence；
- 未解决冲突在摘要和指标上有显著标记；
- 自然语言回答不引用当前用户无权读取的证据；
- 报告升级保留旧版本与生成快照。

## 9. 阶段 6：扩展平台

### 交付物

- Extension Manifest、Capability Grant 和 Lockfile；
- Connector、Mapping Program、Agent、Recipe、Playbook SDK；
- 脚手架、契约测试、Eval Runner、打包和签名；
- 私有 Registry、依赖解析、弃用和撤回；
- 隔离 worker 与资源配额；
- 示例行业包和迁移指南。

### 验收

- 第三方可新增一个 Connector 和 Playbook 而不修改核心代码；
- 依赖冲突在运行前失败并说明原因；
- 已锁定运行不受 Registry 浮动升级影响；
- 被撤回扩展不能启动新生产运行；
- 越权扩展被测试和运行时共同拒绝。

## 10. 阶段 7：行业共享飞轮

### 四条共享链

1. 调研共享：QuestionPack、追问模式、覆盖率指标；
2. 分析共享：FindingPattern、诊断规则、反例和 Eval Case；
3. 程序共享：Connector、Mapping Program、Recipe 和 Renderer；
4. 数据共享：经授权的合成样本、去标识样本和聚合统计。

### 交付物

- Contribution Candidate 和用途授权；
- DLP、去标识、罕见组合和再识别风险检查；
- 联邦评测与汇总指标；
- 行业 Registry、签名、评分、渠道和撤回；
- 资产使用反馈、失败样例和质量分层；
- Flywheel Lift 仪表盘。

### 验收

- 未授权企业原始数据无法进入发布流程；
- 新资产在固定模型/评测集上优于旧版本才可晋级；
- 每项共享资产可追溯许可、发布者、评测和使用范围；
- 下游可收到撤回并定位受影响运行；
- 至少一个行业包显著降低第二家企业的接入或审核工时。

## 11. 阶段 8：整改、结果与规模化

### 交付物

- Recommendation、Action、Owner、Deadline 和 Outcome；
- 基线、目标、复查证据和效果归因；
- 诊断 → 整改 → 结果 → Playbook 更新闭环；
- SSO、企业 Vault、细粒度审计、容灾与合规包；
- 容量规划、队列隔离、成本治理和多地域策略；
- 只读 API、Webhook 和数据产品输出。

### 验收

- Finding 能关联负责人、行动和复查结果；
- 无效建议进入负反馈样例而不是从历史中消失；
- 关键服务满足约定 SLO、RPO 和 RTO；
- 单租户高负载不会挤占其他租户预算；
- 企业可导出自身数据和完整决策证据链。

## 12. 质量指标

每次里程碑至少报告：

- Evidence Coverage：正式 Finding 的证据覆盖率；
- Conflict Visibility：被发现且未静默覆盖的冲突比例；
- Entity Precision/Recall：实体链接精确率与召回率；
- Mapping Reuse：已验证映射程序复用率；
- Reviewer Acceptance：Agent 提案一次审核通过率；
- Unsupported Claim Rate：无充分证据陈述比例；
- Time to First Verified Insight：从接入到首个可信结论的时间；
- Verified Insight Yield；
- Flywheel Lift；
- Cross-tenant Violation：必须恒为 0。

指标按行业、企业规模、数据源和版本切片，避免用总体平均掩盖退化。

## 13. 测试金字塔

- 领域单元测试：不依赖数据库和模型；
- 契约测试：API、事件、Extension、Provider；
- Repository 集成测试：SQLite + PostgreSQL；
- 工作流测试：固定假模型和失败注入；
- Eval：黄金样例、反例、Prompt 注入和冲突场景；
- 端到端测试：从接入到审核报告；
- 安全测试：跨租户、越权、DLP、密钥泄漏；
- 性能测试：大文件、批量事实、并发运行和导出；
- 灾难恢复演练：备份恢复、Outbox 重放和扩展撤回。

LLM 输出不能只靠快照字符串断言，应验证结构、引用、政策、证据充分度和业务评价。

## 14. Definition of Done

一项功能只有同时满足以下条件才算完成：

1. 领域规则和失败语义已明确；
2. API/事件/扩展契约已版本化；
3. 数据迁移和回滚/恢复策略已准备；
4. 权限、租户和敏感级别已覆盖；
5. 审计和可观测性已接入；
6. 单元、集成、契约和必要的 Eval 已通过；
7. 文档、示例和运行手册已更新；
8. 无 secret、企业原始数据或未授权样本进入仓库；
9. 性能和成本在预算内；
10. 产品或领域负责人完成验收。

## 15. 主要风险与应对

| 风险 | 早期信号 | 应对 |
|---|---|---|
| 过早微服务化 | 接口很多但业务闭环不可运行 | 保持模块化单体，以退出条件驱动拆分 |
| 过度依赖向量相似度 | 同名误合并、解释不清 | 确定性标识优先，候选评分 + 人审 |
| Agent 自由群聊失控 | 成本不可预测、无法重放 | 确定性 DAG、预算、状态机、Artifact 黑板 |
| 共享造成隐私风险 | 资产中出现罕见企业组合 | 最小化、DLP、再识别检查、人工发布 |
| 本体成为中央瓶颈 | 所有变化都等待一个团队 | 命名空间、提案分支、版本发布和兼容层 |
| 评测被模型污染 | 分数上涨但真实项目无改善 | 隐藏集、时间切分、人工抽检、结果指标 |
| 数据源持续漂移 | 映射悄悄产出错误事实 | Schema Snapshot、漂移门禁、回放 |
| 扩展依赖冲突 | 环境只在部分机器可运行 | Lockfile、内容摘要、隔离环境和撤回机制 |
| 前端绕开正式流程 | 页面直接改真值表 | 所有写入走领域命令和审核状态机 |
| 在线/离线形成两套系统 | 同一批数据导入结果不同 | 共用 EIP Bundle、Validator、Importer 和 Receipt |
| 总部直连分部数据库 | 网络或 Schema 变化导致数据损坏 | 只接收不可变签名 Bundle，不做数据库复制 |
| 离线介质带入恶意内容 | 解包异常、宏或路径穿越 | 隔离区、大小/路径限制、恶意文件扫描、禁止执行 |
| 增量缺包或重复 | 总部数据不完整或出现重复事实 | 序列哈希链、幂等 Bundle ID、Gap 状态和签名回执 |

## 16. 历史 V1 执行顺序

以下顺序已经形成当前单实例 V1 基线，保留用于解释代码历史；它不再是最新实施顺序：

1. 公共不可变契约和状态机；
2. FastAPI 应用、配置、错误与健康检查；
3. 测试、lint 和类型检查；
4. 可信内核的内存 Repository 原型；
5. SQLAlchemy/Alembic 持久化；
6. Tenant、Workspace、Evidence、Review 和 Audit 的首个纵切；
7. 调研问答导入与合并导出；
8. CRM/ERP/财务语义统一样例；
9. 受控 Agent 工作流；
10. 企业解读前端。
