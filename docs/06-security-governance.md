# 安全、隐私与治理（停用模块）

> 本模块已经从当前产品规划和交付路线中移除。本文仅保留为早期设计档案，不再产生需求、页面、Epic 或验收项。现有程序为维持本地运行所必需的基础身份和凭据代码暂不拆除，但不再扩展。当前权威规划见[管理层企业决策投影总体规划](13-executive-decision-platform.md)。

## 1. 安全目标

平台处理问卷回答、访谈、合同、经营指标和跨系统标识，默认按高敏感企业数据设计。安全不是部署后的附加模块，而是所有数据、Agent、扩展和共享流程的共同约束。

核心目标：

- 原始数据不跨租户；
- 每次读取都有身份、用途和授权；
- 密钥不可进入源码、日志、Prompt、Artifact 或导出包；
- Agent 输出在成为正式知识前经过策略和人工门禁；
- 行业共享只发布经过授权、脱敏、评测和签名的资产；
- 任何关键结论、发布、撤回和权限变化均可审计。

## 2. 威胁模型

首要威胁包括：

1. 租户隔离缺陷导致跨企业查询；
2. 文档中的提示注入诱导 Agent 越权；
3. Connector 或扩展窃取密钥或外传数据；
4. 日志、异常、缓存或向量索引泄露原文；
5. 错误实体合并造成事实污染；
6. 未经授权的原始数据被贡献到行业共享层；
7. 被篡改的本体、程序或 Agent Recipe 进入生产；
8. 模型提供商保留敏感输入或发送到错误地域；
9. 审核账户被盗用或出现权限累积；
10. 删除请求只删除主表、未清除派生数据；
11. 分部数据包在网络或移动介质中被篡改、重放、错投或窃取；
12. 恶意压缩包、路径穿越、宏或可执行内容进入总部；
13. 总部错误信任数据包自报的 Tenant 或分部身份。

每个发布版本都必须维护威胁模型和安全回归用例。

## 3. 数据分级

| 级别 | 示例 | 默认策略 |
|---|---|---|
| Public | 已公开行业本体、公开模板 | 可进入共享注册表 |
| Internal | 一般运行元数据、非敏感配置 | 仅组织内部 |
| Confidential | 问卷回答、业务事实、访谈摘要 | 租户内、加密、受控模型调用 |
| Restricted | 密钥、身份证明、合同敏感条款、个人数据 | 最小访问、强审计、默认不发外部模型 |

分类附着于 Evidence 和 Artifact，并向派生产物传播。较低敏感级别的输出必须经过显式降敏判定，不能自动继承为 Public。

## 4. 身份与授权

身份按部署档位分层：

- `edge_local` 仅绑定回环地址，使用受操作系统边界保护的隐式 Local Owner，不强制平台账号密码；
- `edge_team` 使用本地账户或企业 OIDC；
- `hq_hub` 必须使用 OIDC/SSO、MFA（按企业策略）和强审计，不提供免登录；
- EdgeNode 设备密钥只证明数据包来源，不能代替总部人员身份。

授权采用 RBAC 与 ABAC 组合：

- RBAC 表达角色：Viewer、Analyst、Reviewer、Data Steward、Workspace Admin、Registry Publisher；
- ABAC 表达租户、Workspace、数据级别、用途、地域、时间和资源所有权；
- 高风险操作要求二次确认或双人审核；
- 服务和 Agent 使用短期工作负载身份，不模拟最终用户长期会话。

所有授权先进入统一 Policy Decision Point，领域模块不得自行发明权限语义。

危险配置必须启动失败：Edge Local 不能绑定非回环地址；生产 Hub 不能关闭认证、使用默认密码或缺少审计目标。

## 5. 租户隔离

隔离从 API 到存储全链路执行：

- 入口从受验证身份解析 `tenant_id`，不信任请求体传值；
- 总部导入从已登记 EdgeNode 公钥解析 Tenant 和 OrganizationUnit，不把 Bundle 自报 ID 当授权依据；
- 所有租户数据表包含不可为空的租户键；
- Repository 自动附加租户过滤；
- PostgreSQL 生产环境增加 Row Level Security；
- 对象存储按租户前缀和独立策略隔离；
- 缓存、队列、搜索和向量索引使用租户命名空间；
- 导出任务使用一次性目录并在到期后清除；
- 测试必须包含跨租户负向用例。

行业 Registry 与企业 Workspace 使用不同存储和权限域，不能仅靠一列 `is_shared` 区分。

同一企业集团的分部在总部可属于同一 Tenant，但必须保留 OrganizationUnit、EdgeNode、SourceSystem 和原始记录命名空间。跨分部可见性由用途和角色控制，不能因为同 Tenant 就默认允许所有人员浏览原文。

## 6. 密钥与凭据

采用 BYOK 与托管密钥两种模式：

- 前端只向专用凭据端点提交；
- 后端使用系统密钥或外部 Vault 加密保存；
- API 永不返回完整密钥，只返回提供商、指纹、创建时间和状态；
- Agent 通过短期 `CredentialLease` 间接调用 Model Gateway；
- 日志和错误中统一脱敏；
- 支持轮换、吊销、过期和使用审计；
- `.env` 仅用于本地开发，不进入 Git。

数据库密码、模型密钥和 Connector 凭据必须分开授权，不能复用一个万能 secret。

## 7. 模型网关与数据出境

所有模型调用经过 Model Gateway：

1. 校验任务用途和数据分级；
2. 选择符合地域、保留策略和模型能力的 Provider；
3. 对 Prompt 做最小化和敏感字段处理；
4. 绑定 token、费用、时间和重试预算；
5. 记录模型、参数、知识快照和请求摘要；
6. 校验结构化输出；
7. 执行输出 DLP 和策略检查。

Restricted 数据默认只能使用获批准的私有模型或明确配置的零保留端点。模型网关记录摘要和计量，不默认保存完整 Prompt。

## 8. 提示注入防护

来自文档、网页、问卷和系统字段的内容始终视为不可信数据：

- 指令与证据使用不同结构字段传递；
- Agent 不执行证据正文中的命令；
- Tool 权限由编排器授予，模型文本不能扩大权限；
- 外部链接抓取使用域名、内容类型和大小策略；
- 输出引用必须绑定已存在的 Evidence；
- 高风险工具调用需要策略检查和人工门禁；
- Eval Suite 包含提示注入、越权和数据外传样例。

## 9. 程序与扩展安全

第三方扩展执行前验证摘要、签名、发布者和撤回状态。运行环境默认拒绝网络、数据库和宿主写权限，并设置资源限额。

禁止直接执行 Agent 临时生成的任意代码。Mapping Program 必须来自已审核、已签名、已锁定版本；如未来支持用户代码，必须进入独立沙箱并引入额外 ADR。

## 10. 证据、审核与职责分离

- Agent 只能写 Proposal；
- Reviewer 批准后才生成正式 Artifact；
- 提案作者默认不能独自批准高风险 Finding；
- 本体合并、实体合并、共享发布和权限提升需要 Data Steward 或更高角色；
- 合并使用可逆 Link/Supersede，不破坏源记录；
- 所有人工决策记录理由、时间、身份和前后版本。

## 11. 分部到总部的数据交换治理

在线与离线交换共用 [EIP Exchange Bundle](11-edge-hub-flywheel.md#6-eip-exchange-bundle)：

- 分部显式选择范围并预览数量、敏感度、排除项和用途；
- Bundle 使用总部公钥加密、分部设备私钥签名和逐块内容哈希；
- 模型 API Key、数据库密码、主密钥和设备私钥永不进入 Bundle；
- 总部先验签、校验接收方和限制大小，再解密到隔离区；
- 解包拒绝绝对路径、`..`、符号链接、超额文件数和压缩炸弹；
- 恶意文件、DLP、Schema、序列和幂等检查通过后才可进入 Raw Landing；
- 缺少前序增量时只收进隔离区，补齐前不得提交 Raw Landing、推进确认游标或触发 Agent；
- V1 整包事务提交，任一业务记录失败时不得静默部分导入；
- 相同 Bundle 重放返回原回执，相同 ID 不同哈希按篡改处理；
- 离线介质丢失仍登记安全事件，并根据风险轮换或吊销相关密钥；
- 总部签名回执独立保存，不修改原 Bundle。

分部到总部属于组织内部传输，可在企业政策允许时包含 `raw + confidential + organization_hq` 数据，但不得因此自动获得跨企业共享资格。

## 12. 共享发布治理

企业资产进入行业共享层前必须依次通过：

```text
purpose/consent check
→ data minimization
→ identifier removal
→ DLP
→ rare-combination and re-identification review
→ fixed-suite evaluation
→ human approval
→ signature
→ registry publication
```

默认可共享的是模板、模式、程序和聚合指标，而不是企业原始回答。发布包带有来源许可、用途范围、评测结果、版本、摘要和撤回地址。

## 13. 审计与可观测性

审计事件至少覆盖：

- 登录、授权失败和角色变化；
- Evidence 读取和敏感导出；
- Agent/程序运行及其版本快照；
- 提案批准、拒绝、撤回和冲突解决；
- 密钥创建、使用、轮换和吊销；
- 行业资产发布和下载；
- Bundle 生成、审批、签名、发送、收件、隔离、导入、拒绝、缺包和回执；
- EdgeNode 登记、密钥轮换、吊销和 Release 激活；
- 策略、模型路由和保留规则变化。

审计日志采用追加写、完整性校验和独立保留策略。业务日志使用关联 ID，但不得包含密钥或默认包含 Evidence 原文。

## 14. 保留、删除与备份

每类数据定义保留策略。删除必须覆盖：

- 主记录；
- 对象存储附件；
- 搜索和向量派生索引；
- 缓存与临时导出；
- 可识别的评测样本；
- 备份中的到期删除流程。

审计与已发布聚合资产如依法需保留，应在删除前去标识化并记录法律依据。备份加密、定期恢复演练，并明确 RPO/RTO。

## 15. 发布门禁与安全基线

每次生产发布至少满足：

- 依赖、secret、SAST 和许可证扫描通过；
- 跨租户和越权测试通过；
- 数据迁移可向前执行并具备恢复方案；
- Prompt 注入和输出 DLP 回归通过；
- API/事件契约兼容性检查通过；
- SBOM 和构建来源可验证；
- 高风险变更经过安全审核；
- 回滚手册和告警规则已更新。

任何“为了方便”而绕过租户过滤、证据引用、人工门禁或签名校验的实现都不允许合并。
