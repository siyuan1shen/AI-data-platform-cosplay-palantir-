# 企业统一投影：全项目设计复盘与修改方案

日期：2026-09-15。状态：第一阶段重构已实施；仍保留兼容期的项目数据和旧接口，尚未进行不可逆的跨项目合并。

本轮已落地的范围：公司创建即建立唯一规范投影指针；新建设端只按公司选择并自动解析企业总体投影；发布入口回到建设流程；未发布公司仍可在使用端记录管理观察；本地实例启动不再依赖启动时重写 OpenAPI 和前端类型文件；迁移升级会确定性地选择一个历史主项目，并保留旧项目作为兼容存储。尚未完成的公司级资源归并、时间有效区间和多视图图谱仍按下文的兼容期计划处理，不能把指针兼容层误称为全部资源已经物理合并。

## 1. 结论与审查边界

现有系统的主要问题是业务边界错位：公司是目录，项目却拥有企业知识；建模、发布、接入和管理记录又分别发展出自己的状态与入口。单条接口能运行，并不代表企业能持续维护同一个模型。

本次检查了数据库模型、企业投影与发布服务、查询快照、Agent 运行与规则回退、观察与潜在库、虚拟工作模型、工作观察绑定、系统接入与 Action、前端路由与主要页面、启动器。本文是静态代码审查与既有真实报告测试证据的综合，不代表重新完成了全部浏览器、连接器和采集器测试。没有证据确认的运行问题明确列为待验证。

保留的基础：有类型的对象和多参与者关系、修订校验、变更集、受控动作、原始数据与来源身份、查询快照、多库留痕、工作观察独立采集。优先调整这些能力的归属和衔接，避免重新创造另一套并行模型。

### 对前次验收结论的修正

麦数科技测试证明导入后能运行规则、创建变更、审批并发布，没有证明生成了准确的企业模型。20 个对象和 6 条关系的业务正确性未通过验收；尤其不能把报告提到的业务词自动解释为实际组织单元。该记录应标记为“规则流程测试，业务内容待复核”。既有记录保留，不能为了测试通过而静默删除错误结果。

## 3. 统一产品概念

1. 公司：现实企业边界；每家公司只有一个规范企业知识空间。
2. 企业投影：同一空间中所有有效对象、关系与证据的整体。历史版本、视图、方案不算独立企业。
3. 视图：从同一个对象目录筛选组织、职责、流程、流转或系统数据；布局变化不复制业务对象。
4. 版本：某次接受并发布的结构快照，保留历史。发布表示接受该建模版本，不表示一切内容绝对真实。
5. 草稿变更：相对某个版本的增删改建议，可多份并存；合入时检查基线和字段冲突。
6. 方案：对未来组织/流程的假设性修改；未确认时不能覆盖当前状态。
7. 项目：可选的建设任务/专题标签，记录目标、材料集合、对话与变更，不拥有一套企业数据库。第一版普通页面不要求用户创建它。
8. 会话：一段任务讨论；删除会话不删除独立保存的材料、模型、观察和历史动作。
9. 法人公司与业务部门分别建模；将来需要集团汇总时以明确企业集合只读聚合，不把公司隔离全部取消。

## 4. 最终用户流程与页面

### 建设端：三个入口

**企业**：创建/选择公司，显示当前发布状态、材料/数据覆盖；自动建立企业空间。

**企业建模**：材料上传 → 预览 → 确认导入 → Agent 提取现状/建议/未知 → 差异草案 → 图形与详情编辑 → 确认 → 发布。右侧图与当前草稿绑定，点击对象可增改、退役、查看来源。继续上传材料只更新候选，不另建投影。

**系统接入**：登记一次源系统 → 检查结构/样本 → 原始快照 → 建议映射 → 身份匹配 → 冲突审核 → 验证 → 查询/导出。直接选择现有岗位/订单/客户类型，不要求重新建模。不接系统不影响前述建模、发布与探索。

模型配置、备份和扩展从全局设置进入；普通用户不直接操作 JSON 配置，保留高级编辑器给扩展开发者。

### 使用端：两个入口

**企业数字投影**：默认组织与岗位；内部切换职责权限、业务流程、信息/资金/物流/指令和系统数据视图。工作观察放岗位详情。顶部显示企业、模型版本、数据截至时间及未核实内容提示。

**管理 Agent**：输入会议、观察或问题；识别意图后显示“保存观察”或执行查询。查询结果卡片附来源，复杂任务提供事实、观察、假设、冲突、缺口、方案与取舍。潜在候选逐项确认；计划预览与执行能力明确区分。

初次未发布：可以保存观察与根据材料探索；询问正式职责或业务金额时说明尚无正式模型/数据，提供下一步入口。

## 5. 数据与服务修改规范

### 5.1 企业空间与身份

- 新增 EnterpriseSpace，一家公司唯一对应一个空间，数据库唯一约束 company_id。
- Entity、Relation、OntologyType、SourceDocument、SourceSystem、SourceIdentity、映射、发布、查询快照等迁移到 enterprise_space_id；跨库记录共同携带公司/空间 ID 并验证一致性。
- 原 project_id 保留为历史来源；未来 work_item_id 可空。禁止通过“默认项目＋跨项目 union 查询”长期模拟统一空间。
- 实体 ID 跨版本稳定；企业登记记录与图中公司实体建立明确一对一引用，不复制公司档案字段作为第二权威源。
- 区分部门、岗位、员工、职责、流程、能力。一个员工可任多个岗位，同名岗位不自动合并；任职/归属带生效时间。
- ERP/CRM 中一个源主键绑定一个规范实体；匹配键包含来源系统与对象类型，不能只比较显示名称。

### 5.2 正式、观察、潜在与控制

- 正式库：企业对象目录、认可的结构断言、映射与验证数据；包含来源和有效时间。
- 观察库：原始访谈/会议/工作活动及抽取断言，保留原文定位。稳定材料与日常输入可用不同类型和处理规则，但共用来源引用规范。
- 潜在库：管理者确认保留的假设/经验；确认表示值得纳入，不表示因果已证实；支持驳回、撤销、重新开启及证据变更提醒。
- 控制库：任务、读取清单、工具运行、确认与迁移索引。现有控制索引含 statement/route_payload 等内容，需明确哪些是执行记录、哪些是业务正文；避免再复制一套业务权威数据。
- 现有多库暂不物理合并，先统一权威归属。跨库写入用已有 outbox/恢复机制＋幂等操作；全库备份与恢复作为整体校验。
- 会议观察不再双写 MeetingRecord 和 ManagementObservation 两份可独立编辑正文；旧接口返回统一观察的兼容视图。
- 虚拟工作模型的观察断言、证据与历史保留；正式已知岗位直接引用企业实体。行为节点如“使用 CRM”可独立存在，不能强制都变成组织实体。

### 5.3 来源、事实与时间

所有抽取项标注：现状陈述 / 设计规定 / 系统记录 / 改进建议 / 潜在假设 / 未知；另设来源、支持/反证、人工审核与业务生效时间。来源类型与可信状态分开，不能用一个 viewpoint 代替所有状态。

具体回归样例：

- “无研发部门”只能记录否定/缺口，不能创建研发部门。
- “建议建立财务预算流程”进入建议，不能直接成为正在执行的流程。
- “员工通过企业微信沟通”不证明存在人力资源部，也不证明正式汇报关系。
- 三份报告互相矛盾时保留陈述时间和适用范围，展示冲突；后来的报告不必然覆盖前文。
- 有引用但引用不支持结论，仍属未通过业务验证。程序校验引用归属、版本、原文位置与类型，语义抽取仍需模型和人共同审核。

### 5.4 发布与查询

- 草案 → 结构校验 → 来源核对 → 人工接受 → 应用 → 发布，用户可在同一页面完成。
- 保留当前变更集的并发修订检查；提交过时草案返回 409，重新生成差异，不用最后一次写覆盖。
- 结构版本、映射版本和数据水位分开。一次 ERP 增量导入不生成新的组织架构版本。
- 查询基线固定 company/space、publication_id、mapping_version_refs、data_cutoff/batch_refs、observation_version_refs 和过滤范围。
- 图表、管理查询、导出必须使用同一基线；明确历史时点采用“当时所知”还是“事后修正”口径，默认前者，后者显式选择。
- 原发布快照只读保留；版本切换不重绑定历史证据。未绑定系统对象进入候选目录，不能为了查询方便自动进入组织图。

### 5.5 Agent、工具与 Action

- 三种职责保持：企业投影、本体接入、管理；管理输入/输出是同一窗口的内部流程。
- 共用企业对象目录与版本化读取服务；对话上下文可以分开，企业知识不随对话分开。
- 建模工具：查询来源、查询现有对象、提出变更、预览/验证变更。手动编辑也走同一变更服务。
- 本体工具：读取结构/样本、生成映射候选、检验身份/单位/时间口径、查询/导出已验证数据。
- 管理工具：读取正式数据、搜索观察/潜在记录/工作观察、生成候选和方案；结构修改提交到建模草案。
- SIMPLE 必须匹配已注册的确定性查询及可用数据；失败返回缺数据/需澄清，不悄悄转成猜测。COMPLEX 允许跨库检索并记录实际读取范围，不要求每次把全库塞入上下文。
- 任务路由、归属校验、金额计算、分页、导出、状态推进交给程序；业务理解、探索与方案权衡交给模型。
- 未配置模型时准确显示不可用的智能能力；纯读取、手动建模和导出继续可用。模拟器显式独立环境，模拟草稿禁止正常发布。
- 工具 status 与 task_outcome 分离：完成工具调用不等于回答问题。task_outcome 至少有 answered/partial/needs_input/unsupported；显示未完成原因。
- Action 核心只支持内部任务/草案/候选/导出。ERPNext 等通过扩展注册，声明只读或写入、副作用、预览、支持范围与结果确认方式；默认不注册外部写入。
- 真实效果记录独立于工具结果，生成方案不能被称为“已执行企业改进”。

### 5.6 工作观察

- Collector 独立发布，管理员配置公司与设备关联；员工无须选择项目。
- 在线和离线包共用公司级来源/事件去重。调岗绑定带业务有效区间，断网补传按 observed_at 归属。
- 观察统计挂到企业岗位/员工，展示覆盖、缺口、重叠设备及统计区间；不自动改变正式流程。
- 比较只表达活动路径差异；绩效关联必须另有相同口径的结果数据，不以路径短证明效率高。

## 6. 接口、迁移与兼容

接口仍为 /api/v3，新增公司入口并统一资源语义：

```text
/companies/{company_id}/projection
/companies/{company_id}/materials
/companies/{company_id}/changesets
/companies/{company_id}/publications
/companies/{company_id}/source-systems
/companies/{company_id}/semantic-datasets
/companies/{company_id}/agent-threads
/companies/{company_id}/observations
/companies/{company_id}/potential-records
/companies/{company_id}/work-observation
```

异步任务继续返回 operation_id，长任务 202；预览绑定内容摘要与过期时间；重复导入幂等；标识相同而内容不同显示冲突。前后端 OpenAPI 同一次改动生成类型，禁止只改导航文字。

迁移步骤：

1. 确认实际运行实例和全部数据目录；生成包含正式/观察/潜在/控制及附件的可恢复备份，先演练恢复。
2. 新增空间与 ID 映射表，先不删除旧字段或旧项目；输出公司→旧项目→资源数量清单。
3. 单项目公司直接映射到唯一空间；多项目公司的材料、对象、关系、映射分别预览归并。
4. 保持旧实体 UUID；只有可靠身份依据和人工裁决才能合并重复对象，生成别名映射并迁移全部引用。相同名称不是合并依据。
5. 发布历史保存 legacy_project_id；不拼接旧快照伪造过去的统一版本。归并后创建新的企业基线，保留冲突来源。
6. 同步迁移潜在、观察、工作观察、对话、动作和来源引用；核对数量、哈希、悬空引用、有效时间和查询结果。
7. 老 /projects/... 路由映射到新空间并保留原项目来源；历史深链能定位原记录。写入统一交给新服务，避免双写分叉。
8. 完成公司范围服务后切前端、缓存键和深链。兼容期内记录旧接口使用情况，所有调用迁完才移除旧领域路径。
9. 迁移失败恢复完整实例；不允许只回滚一个数据库留下跨库半迁移。数据迁移时禁止业务写入，恢复校验后再开启。

麦数科技旧验收项目须保留对话、原报告、动作和发布历史，并标注模拟来源。不得把旧规则生成的节点无审核地当作新基线。测试服务的数据在 Temp 目录，不能保证桌面默认启动就能看到；修复交付时必须提供稳定实例或可恢复公司包与入口。

## 7. 可执行工作包与依赖

| 顺序 | 交付内容 | 主要修改位置 | 完成条件 |
| --- | --- | --- | --- |
| A | 基线盘点、运行实例识别、四库/附件备份恢复演练、修正验收状态 | scripts、config、archives、验收文档 | 重启仍可找到旧数据；备份能恢复 |
| B | 禁止隐式规则建模、明示实际模型与业务结果、否定/建议测试集 | agent_runtime、AgentWorkspace、模型配置 | 无模型不伪装完成；测试输出不能进入正常发布 |
| C | 公司唯一空间、稳定身份、兼容层、迁移预览与回滚 | models、migrations、portfolio、dependencies、各库范围校验 | 同公司多旧项目共用目录，不跨公司读取 |
| D | 统一来源/观察/潜在流转、虚模实体引用、时间归属 | observations、potential、virtual_work、work_observation | 同输入只有一个权威记录，来源与历史可追踪 |

| F | 公司级接入与身份映射、统一查询基线、图/Agent/导出一致 | integration、semantic_datasets、query_snapshots、ProjectionPage | 系统增量无需重建组织，导出可按来源复核 |
| G | 统一管理会话、未发布时输入、候选确认、Action扩展边界 | task_routing、tool_registry、actions、ManagementAgentPage | 复杂任务可解释，外部写入默认不可用 |
| H | 简化导航、业务视图、来源抽屉、按需加载、旧深链兼容 | App、AppShell、WorkspaceContext、图组件 | 普通用户只选公司，全流程不用手写 JSON |
| I | DOCX 故障定位与浏览器回归、三类企业真实验收、启动与文档 | imports、http、scripts、tests、docs | 不能靠 API 绕行宣称前端完成 |

依赖：A → C → D/E → F/G → H/I；B 可在 A 后独立推进，导入故障定位可并行。所有团队先固定公司范围、版本/来源契约及验收样例，再分别修改前后端。避免各自新增另一套接口和状态。

本轮不引入新的项目管理平台、图数据库、向量库、因果推断引擎或行业业务系统。现有数据库与图组件足够支持这轮归属修正；性能先通过公司范围索引、分页、按需图加载和减少重复读取改进。

## 8. 必须通过的验收

1. 创建公司后直接导入资料，无创建项目前置；新对话仍查询相同企业对象。
2. 一家公司导入三次报告，形成一份可增量修改的模型；每条关键结论能回到原文，否定与建议不会当成现状。
3. 对麦数报告人工建立预期清单后使用真实配置模型测试；记录实际模型、提示、来源、草稿、纠错。不能复用 MOCK 的数量作为业务正确基准。
4. 图中修改岗位、职责、关系及退役都进入差异与历史；两份并发草案修改同一字段产生可处理冲突。
5. 无模型配置仍能手动维护和导出；智能任务清楚返回需配置状态。模型失败、无效输出、工具失败不生成假成功。
6. 未发布公司可以保存管理观察；正式查询被明确限制；发布后原观察可继续用于复杂分析。
7. 同公司 ERP 与 CRM 的客户身份可对齐；同名异物不自动合并；已验证查询与导出保持同一快照。
8. 同公司不同历史项目的数据迁移可预览、可恢复；另一个公司的同名人员/客户不被读入。
9. 一次输入在会议视图、管理对话和观察查询中指向同一个记录；确认潜在候选有留痕，不自动提升为正式事实。
10. 任职变更后的离线补传仍按历史生效时间归属；不同员工路径不拼接；同事件重复导入不增计。
11. 图、Agent 和导出明确且一致地显示结构版本与数据时间；切换历史版本能重现结果。
12. 普通二元关系图、岗位下钻和证据原文可通过浏览器操作；图实际完成渲染，不能以对象计数代替图形验收。
13. 采集器、接入、Agent、发布和 Action 的正常/失败/重试/取消状态有明确信息；外部执行未支持时返回未支持。
14. 真实浏览器完成 DOCX 预览与确认。若自动化工具故障，单独记录环境问题；在用户实际浏览器验证前该项保持未通过。
15. 桌面重启后能看到同一公司、资料、对话、版本及测试记录；报告与真实数据不进入公开仓库。

最终判据：一家企业持续积累一份可核查的数字投影，用户无需理解项目、数据库或 Agent 内部划分即可完成建模、接入、观察输入和管理查询。
